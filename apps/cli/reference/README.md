# Bake profile launcher reference

The `bake-cli` launcher starts Bake's Node runtime through a named Cordis profile. The shipped profiles are `tui` for the terminal agent and `headless` for one task. [Launcher overview](../README.md) owns the common commands.

<a id="profile-boot"></a>
## Profile boot

Each profile keeps its bundle list and optional `cordis.patch.yml` under `$DSH_HOME/profiles/<name>`. The launcher applies bundle, profile, home, and invocation patches in that order. First use initializes a shipped profile; an existing profile keeps its selected bundles. A missing bundle fails startup.

The launcher parses its own profile flags and forwards the remaining arguments to the application. `--from-default-profile <template>` creates a custom profile from a shipped template; `--dump-default-config` and `--dump-config` inspect composition without starting the agent.

<a id="source-execution"></a>
## Source execution

From the repository root, `bun run build` builds the Node runtime and TUI, and `bun run start` launches the built terminal agent. `bun run dsh` runs the built profile launcher. Bake uses `~/.bake` unless `DSH_HOME` selects another home. External profile package installation remains pnpm-managed and is separate from the Bun source workspace.

<a id="startup-diagnostics"></a>
## Startup diagnostics

When a required plugin fails activation, the launcher reports failed and pending plugins, missing services, and the original error. It writes a uniquely named startup report under the selected home’s `logs/` directory when possible; failure to write the report is also printed to stderr. The process exits with status 1. Raw plugin errors may contain configuration values, so review a report before sharing it.

<a id="config-schema-dump"></a>
### Config schema dump

`--dump-config-schema` uses the same bundle, profile, home, and argv patch layers as `--dump-config`, including repeatable `--patch` and `--from-default-profile`. The three dump flags are mutually exclusive and reject app arguments and the reserved `desktop` profile. Successful composition produces one pretty-printed JSON Schema 2020-12 document on stdout. Its root describes the parsed entry list printed by `--dump-config`; `$defs.patchList` separately describes profile/home/CLI overlays. Keep the document's `$defs` when validating that fragment. Preparation, patch parsing/composition, or resolution-setup failures exit nonzero without a schema. Collection and projection failures retain partial output and exit 1; diagnostics also appear on stderr. This includes `partial` projections and omitted non-JSON annotations even when stdout contains a valid, useful schema. Schema-dump unmatched-target warnings do not carry layer labels; use `--dump-config` with the same layers for source-labelled warnings.

Plugin Config fields, defaults, descriptions, and supported constraints are projected from native Schemastery declarations. Ordinary fields are inline; shared Configs and recursion use `$ref`. JSON Schema defaults are annotations, not default insertion. Required fields account for whether Schemastery's nullable fallback can pass validation. Unions use `anyOf`, while native execution still selects its first successful branch. Role metadata such as `secret`, `credential-ref`, and `ms`, plus `volatile` live-update metadata, remains in `x-cordis` annotations. Invalid volatile containment is a schema-definition error; field input types do not become reference-object types. Callback validation, unsupported regex semantics, and other unprojected constraints are marked partial rather than silently discarded. Non-finite bounds and non-JSON default/presentation annotations are omitted with limitations while structural fields remain available. Object constants retain ordinary nullable-member constraints, but inherited-property comparison is marked partial. Unrepresentable defaults, unsupported intersections, and unresolved recursive-default dependencies retain unknown omission behavior; native validation is still required.

Parse YAML with the Cordis entry-list dialect: `!!js` scalars become inert `{ "__jsExpr": "..." }` markers. Ordinary Config values and entry `disabled` accept these markers without evaluating their results. Group lists and Include fields stay literal. Entry ids are optional; non-insert patches without a nonempty id are accepted as no-ops with a Loader warning. A disabled entry may omit required Config unless `group: true` forces activation; a disabled expression also leaves omission undecided until runtime. Supplied Config values are still validated. `disabled` accepts booleans, null, and expression markers; other truthy values that the Loader coerces are rejected. Children of a disabled group or include without `group: true` are not validated because the Loader never creates them. Children under a disabled `group: true` row and patch insertions into a disabled group are validated as enabled, although the Loader keeps ancestor-disabled children uninitialized. Known root-tree targets validate whole Config replacements, not deep partial objects. Include-local ids and sequence-dependent targets introduced or changed by earlier patches are not inferred. Unknown plugin names remain open, and differing resolutions of one name use a union with an ambiguity diagnostic.

The root `x-cordis` annotation contains `profile`, `complete`, `entries`, `diagnostics`, and `patchSchema`. Entries retain traversal order with `path`, optional `id`, `name`, `status`, and `configRef`; statuses are `schema`, `partial`, `absent`, `unsupported`, or `error`. Optional `tree: "group" | "include"` identifies native carriers: they can have `status: "absent"` because no Config is exported, while `configRef` points to the Loader structure definition. Malformed inspected rows receive positioned errors without discarding valid siblings; `name` is omitted when no literal name exists. Invalid list containers or include-patch composition failures produce carrier-level diagnostics; failed composition leaves that include's children unavailable rather than reporting unpatched or filtered children as final. A disabled carrier without `group: true` may omit its config and is recorded as a childless tree. Projection limitations are repeated at every entry sharing that Config. An absent Config means unknown fields, not forbidden configuration. Discovery paths append `/config/<index>` for group children and `/include/<index>` for included children; the latter are not JSON pointers into the root dump. `complete` is false for any error diagnostic, any `partial`/`unsupported`/`error` entry, or one plugin name mapping to multiple Config definitions. This reference covers declarations, including disabled rows: their import or include failures can make a bootable profile incomplete. Runtime-generated preset/client trees and plugin startup checks are outside this reference; conversely, `complete` does not guarantee successful boot.

Earlier union branches that may alter inputs and dictionary keys that may rename/collide require relaxed validation. Lazy metadata propagation may affect shared nodes beyond the current Config, so that Config retains available declaration details alongside an unrestricted alternative rather than simulating native mutation. These cases are partial and require native validation.

Collection imports trusted modules and may invoke Config getters and lazy builders, but never applies plugins, executes transform callbacks, or evaluates configuration expressions. Imports can block or retain process handles before or after output; automated callers should enforce an external timeout. The dump does not force-exit or own disposal of import-time resources. Ordinary import/builder stdout is routed to stderr; direct file-descriptor writes are not intercepted. Profile preparation retains YAML dump initialization writes. Only schema declarations are emitted, not actual configured values; declared defaults and raw plugin errors can still contain sensitive data. Review output before sharing. See [app-boot](../../../packages/boot/app-boot/README.md) for the collector API.

Treat the output as a regenerated, pre-stable reference, not a versioned persisted catalog. `$schema` identifies the JSON Schema validation dialect; `x-cordis` follows dsh releases. Regenerate after changing dsh or plugins, and follow `$ref` and `configRef` rather than hard-coding definition names, ordering, or text. Incompatible dialect changes select a new `$schema`; annotation changes do not use Session-format migrations.
