# 终端性能诊断

[English](README.md) | 中文

## 概述

无需 API 密钥或用户数据，即可测量全新 TUI 进程、恢复混合历史，并在定速响应期间输入文字。报告保留各次样本、每种工作负载的中位数以及失败记录。此本地诊断没有经过校准的耗时阈值，不能用于判定 CI 性能是否合格。

## 运行

需要已构建上游库的检出目录、根目录 `package.json` 固定版本的 Bun、Node，以及 macOS 或 Linux。参见[构建前提](../../../PLAN.md#132-build-from-a-clean-checkout)。在仓库根目录运行，并停止其他 CPU 密集型验证：

```sh
./tui/scripts/tui.ts perf --workload fresh --workload typical --samples 3 --output /tmp/bake-bun-native-production.json
```

协调器和原生 PTY 在 Bun 上运行；应用的共享打包器提供被测产物。夹具生成和每个被测 Harness 进程均使用所选 Node 可执行文件。每次调用创建独立的包、配置、工作区和会话存储，并在成功或失败后清理这些资源。构建后的 `dsh --profile tui` 使用应用的实际组合补丁和 Harness 重放适配器启动，不修改已安装的用户配置。

`--workload` 选择工作负载，可重复指定。`--node` 选择被测运行时。`--mode production` 为默认值，与构建后的应用一致。`--mode development` 选择未压缩的开发基线及开发版 React/Ink：

```sh
./tui/scripts/tui.ts perf --mode development --workload fresh --workload typical --samples 3 --output /tmp/bake-bun-native-development.json
```

`--cpu-profile <目录>` 为每次样本启用 Node CPU 分析。启用分析后的耗时包含分析开销，应与普通样本分开。超时、崩溃、缺少历史回答、重复历史回答、缺少最后一个增量或退出异常都会使样本失败。诊断继续运行其余样本，每完成一次便更新 JSON 报告，只要有失败便以非零状态退出。Ctrl-C 或 SIGTERM 会中断观察、等待当前进程清理完成，并停止其余样本，以非零状态退出并在报告中标记中断。比较中位数之前先检查每个失败。

<a id="measurement-reference"></a>

## 测量参考

报告中的产物哈希标识私有包、启动模块、夹具写入器、预加载模块、组合补丁和依赖锁文件。运行期间需保持上游构建库不变；这些库仍作为外部模块导入。

| 测量 | 包含的终点与限制 |
|---|---|
| `readyMs` | 从启动到粘贴模式注册及观察到输入框回显，包含历史重放，不包含夹具生成和打包。 |
| `idleInputMs` | 五次写入到对应输入框回显；汇总取各样本最大值的中位数。 |
| `liveInputMs` | 首个响应增量之后的草稿输入到其输入框回显。 |
| `firstDeltaMs` | 提示提交到首个可见合成增量。 |
| `streamMs` | 提示提交到最后增量及随后的空闲状态，包含刻意设置的 10 ms 重放间隔。 |
| 内存 | 就绪时和流式输出结束后，主隔离实例强制 GC 前后的堆数值，此时会话状态仍可访问。汇总保留堆使用就绪时 GC 后的值，不包含工作线程的堆。 |
| RSS 峰值 | 主 Node 进程生命周期的最大值，包含工作线程，不包含 Bun 协调器及独立子进程。 |
| 输出 | 启动、空闲输入和流式输出的 PTY 总字节数；历史标记计数覆盖有限捕获尾部之外的输出。 |

终端视口为 120 列、40 行。计时使用协调器的单调时钟和 2 ms 观察轮询；PTY 字节到达不等同于终端模拟器绘制或键盘硬件延迟。每次样本使用全新进程和独立文件，但不清空文件系统缓存。1 GiB V8 堆上限是诊断资源约束，不是产品限制。GC 采样位于输入计时间隔之外，可能影响后续分配行为。这些测量不包含真实推理或网络延迟、交互式会话选择器列表、反复导航、压缩或图像接收。

<a id="workloads-and-assertions"></a>

## 工作负载与断言

[夹具生成器](history.ts) 通过 Harness API 构造固定会话事件。每个历史回合包含多语言提示、推理、文字和紧凑流增量；每第四个回合添加一次工具调用及 128 行结果文字。工具内容是合成历史记录，并不执行工具。独立的小型重放夹具提供一个含 100 个增量的响应，避免重放适配器设置时再次解析被测历史。

| 工作负载 | 已完成回合数 | 用途 |
|---|---:|---|
| `fresh` | 0 | 配置启动基线 |
| `small` | 50 | 短会话恢复 |
| `typical` | 500 | 混合长历史恢复 |
| `tail` | 2000 | 大型历史的瞬时分配压力 |

这些是合成工作负载标签，并不代表实测用户会话分布。报告包含准确的事件、增量、工具及持久化字节计数。每个历史回答在恢复、输入和流式输出全过程中必须恰好出现一次。每个成功样本必须观察到最后模型增量、回到空闲状态并正常退出。[夹具测试](../tests/performance.spec.ts) 验证确定性重放与失败汇总；[PTY 生命周期测试](../tests/performance-terminal.test.ts) 覆盖失败退出、致命信号、取消和超时后的清理。

<a id="dev-note"></a>

## 开发备注

当前 Bun 原生对比使用相同的源码哈希、视口和夹具，每种工作负载各采集三个样本：[开发模式](results/bun-native-development.json)和[生产模式](results/bun-native-production.json)。生产构建将插件从 104,323 字节缩小至 58,820 字节。500 回合就绪中位数从 6197 ms 降至 5114 ms（17.5%），RSS 峰值从 909.4 MiB 降至 804.8 MiB（11.5%）。保留堆分别为 58.1 和 56.4 MiB；流式期间输入分别为 2.14 和 2.26 ms，接近 2 ms 的观察间隔。全新会话就绪分别为 1321 和 1281 ms。这些测量支持选择生产版 React，并不意味着 Bun 执行 Harness 更快。[原生驱动的尾部样本](results/bun-native-tail.json) 在 1 GiB 上限下恢复 2000 回合时仍失败；驱动记录了 Node 的 SIGABRT 和堆耗尽消息。

[Node 24 的单次生产样本](results/bun-native-node24.json) 在 5540 ms 内完成 500 回合恢复，RSS 峰值为 857.5 MiB，流式期间输入观察为 2.27 ms。构建后的重放、导航、附件和终端恢复在 Node 24 与 26 上也均通过。下方较早的 script 驱动测量保留各自的产物和驱动上下文，其样本不与 Bun 原生对比混合汇总。

2026-09-22 在 macOS x64 上采集的本地证据：[Node 26 开发模式](results/node26-development.json)、[Node 26 生产模式](results/node26-production.json)和 [Node 24 开发模式](results/node24-development.json)。JSON 文件保留产物哈希及未经更改的数值样本，省略原生失败堆栈。这些是诊断观察，不是可移植的性能预算。下表每个 Node 26 行均为三个成功样本的中位数；尾部工作负载则报告失败。

| 模式 / 回合数 | 就绪，ms | 最大空闲输入，ms | 流式期间输入，ms | 保留堆，MiB | RSS 峰值，MiB |
|---|---:|---:|---:|---:|---:|
| 开发 / 0 | 1231 | 4.90 | 2.08 | 46.1 | 219.8 |
| 开发 / 50 | 1879 | 2.21 | 2.10 | 48.2 | 297.8 |
| 开发 / 500 | 5962 | 5.06 | 2.08 | 58.1 | 908.8 |
| 生产 / 0 | 1223 | 4.87 | 2.18 | 45.9 | 215.1 |
| 生产 / 50 | 1652 | 2.17 | 2.14 | 47.8 | 267.2 |
| 生产 / 500 | 4946 | 4.72 | 2.21 | 56.4 | 800.0 |
| 任一模式 / 2000 | 3/3 堆耗尽 | — | — | — | — |

Node 24.21.0 的单次开发模式样本中，全新会话在 1294 ms 后就绪，500 回合在 6649 ms 后就绪，后者 RSS 峰值为 1000 MiB。其 2000 回合样本也在输入注册前耗尽堆。这是运行时兼容性观察，不是多次重复的 Node 版本对比。

500 回合夹具包含 3251 个持久事件、20,500 个增量、125 个工具和 3,561,500 个持久化字节。2000 回合夹具包含 13,001 个事件、82,000 个增量、500 个工具和 14,264,383 个字节。独立的 [CPU 分析摘要](results/cpu-profile-summary.json) 显示了较多 ANSI 差异处理、垃圾回收、Yoga、Ink 输出和开发版 React 工作。该分析覆盖整个进程，未单独隔离恢复阶段。

布局后续工作是限制初始历史渲染的分配量，同时保留有序完整的回滚输出及每个回答只输出一次的行为。当前完整历史重放的瞬时占用远大于保留堆。生产构建是经过测量的候选方案：此处 500 回合就绪耗时约降低 17%，RSS 峰值约降低 12%，但未解决尾部失败。应用的共享构建使用生产编译和运行时选择。布局代码仍在此诊断范围之外。渲染修改后需再次运行相同工作负载，才能声称长历史验证通过。
