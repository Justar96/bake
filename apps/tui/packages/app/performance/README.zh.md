# 终端性能诊断

[English](README.md) | 中文

## 概述

无需 API 密钥或用户数据，即可测量全新 TUI 进程、恢复混合历史，并在定速响应期间输入文字。报告保留各次样本、每种工作负载的中位数以及失败记录。此本地诊断没有经过校准的耗时阈值，不能用于判定 CI 性能是否合格。

## 运行

需要已构建共享库的检出目录、根目录 `package.json` 固定版本的 Bun、Node，以及 macOS 或 Linux。参见[开发指南](../../../../../docs/development.zh.md)。在仓库根目录运行，并停止其他 CPU 密集型验证：

```sh
bun apps/tui/scripts/tui.ts perf --workload fresh --workload typical --samples 3 --output /tmp/bake-bun-native-production.json
```

协调器和原生 PTY 在 Bun 上运行；应用的共享打包器提供被测产物。夹具生成和每个被测 Harness 进程均使用所选 Node 可执行文件。每次调用创建独立的包、配置、工作区和会话存储，并在成功或失败后清理这些资源。构建后的 `dsh --profile tui` 使用应用的实际组合补丁和 Harness 重放适配器启动，不修改已安装的用户配置。

`--workload` 选择工作负载，可重复指定；省略时运行全部六种工作负载。`--node` 选择被测运行时。`--mode production` 为默认值，与构建后的应用一致。`--mode development` 选择未压缩的开发基线及开发版 React/Ink：

```sh
bun apps/tui/scripts/tui.ts perf --mode development --workload fresh --workload typical --samples 3 --output /tmp/bake-bun-native-development.json
```

`--app-artifacts <目录>` 使用当前夹具写入器测量已保存的 `index.js` 和 `startup.js` 应用包。驱动将这些包复制到私有应用目录，使依赖正常解析。请提供按所选模式构建的产物，并将可选的 `metadata.json` 放在同一目录，以记录来源。未指定此选项时，驱动从当前检出构建应用。

`--cpu-profile <目录>` 为每次样本启用 Node CPU 分析。启用分析后的耗时包含分析开销，应与普通样本分开。超时、崩溃、缺少历史回答、重复历史回答、缺少最后一个增量或退出异常都会使样本失败。诊断继续运行其余样本，每完成一次便更新 JSON 报告，只要有失败便以非零状态退出。Ctrl-C 或 SIGTERM 会中断观察、等待当前进程清理完成，并停止其余样本，以非零状态退出并在报告中标记中断。比较中位数之前先检查每个失败。

## 测量参考

报告中的产物哈希标识私有包、启动模块、夹具写入器、预加载模块、组合补丁和依赖锁文件。`applicationSource` 区分检出构建与外部提供的产物，并保留其可选来源信息。只有检出构建记录 `sourceSha256`；外部二进制文件记录各自产物的哈希。对比期间需保持已构建的共享库不变；这些库仍作为外部模块导入。

| 测量 | 包含的终点与限制 |
|---|---|
| `initialInputMs` | 粘贴模式注册后，首次探测写入到其输入框回显；此时尚未等待完整历史重放。 |
| `firstInputMs` | 从启动到首次观察到输入框回显。`historyMarkersAtFirstInput` 记录此时已到达的历史标记数量。 |
| `readyMs` | 从启动到首次输入框回显及全部预期历史标记到达；若有末尾工具结果，也包含其标记。不包含夹具生成和打包。 |
| `idleInputMs` | 五次写入到对应输入框回显；汇总取各样本最大值的中位数。 |
| `liveInputMs` | 首个响应增量之后的草稿输入到其输入框回显。 |
| `firstDeltaMs` | 提示提交到首个可见合成增量。 |
| `streamMs` | 提示提交到最后增量及随后的空闲状态，包含刻意设置的 10 ms 重放间隔。 |
| 内存 | `readyMemory` 和 `settledMemory` 分别记录就绪时和流式输出结束后，主隔离实例强制 GC 前后的堆数值，此时会话状态仍可访问。汇总的 `retainedHeapMiB` 和 `settledRetainedHeapMiB` 使用对应的 GC 后数值，不包含工作线程的堆。 |
| `peakRssMiB` | 流式输出结束后观察到的主 Node 进程生命周期最大值，包含工作线程，不包含 Bun 协调器及独立子进程。 |
| 输出 | `initialBytes`、`idleBytes` 和 `streamBytes` 分别统计就绪前、随后空闲输入及流式输出期间的 PTY 字节数。`historyMarkerOccurrences` 统计的历史标记覆盖有限捕获尾部之外的输出。 |

驱动在字节到达时记住粘贴模式注册状态，也能识别跨数据块的转义序列，因此注册序列离开有限捕获尾部后，注册状态仍然保留。首次输入可以早于完整重放；就绪还要求全部历史标记到达。整个样本期间均可观察标记数量和身份。

终端视口为 120 列、40 行。计时使用协调器的单调时钟和 2 ms 观察轮询；PTY 字节到达不等同于终端模拟器绘制或键盘硬件延迟。每次样本使用全新进程和独立文件，但不清空文件系统缓存。1 GiB V8 堆上限是诊断资源约束，不是产品限制。GC 采样位于输入计时间隔之外，可能影响后续分配行为。这些测量不包含真实推理或网络延迟、交互式会话选择器列表、反复导航、调整窗口大小、压缩或图像接收。

## 工作负载与断言

[夹具生成器](history.ts) 通过 Harness API 构造固定会话事件。每个历史回合包含多语言提示、推理、文字和紧凑流增量。默认组合每第四个回合添加一次工具调用及 128 行结果文字；`tools` 每个回合添加四次调用。工具内容是合成历史记录，并不执行工具。独立的小型重放夹具提供一个含 100 个增量的响应，避免重放适配器设置时再次解析被测历史。

| 工作负载 | 已完成回合数 | 工具数 | 历史标记数 | 用途 |
|---|---:|---:|---:|---|
| `fresh` | 0 | 0 | 0 | 配置启动基线 |
| `small` | 50 | 12 | 50 | 短会话恢复 |
| `typical` | 500 | 125 | 501 | 混合长历史恢复 |
| `tail` | 2000 | 500 | 2001 | 大型历史的瞬时分配压力 |
| `tools` | 500 | 2000 | 501 | 密集工具调用及结果 |
| `large-output` | 12 | 3 | 193 | 64 KiB 助手回答 |

每个普通回答以唯一历史标记结束。每个 `large-output` 回答包含十六个 4096 字节的段落，每段一个标记，覆盖全部 64 KiB。若最后回合有工具，其最后工具结果会在结果文本后添加一个标记，使就绪包含末尾工具输出。恢复、输入和流式输出全过程中，每个预期标记必须恰好出现一次。

这些是合成工作负载标签，并不代表实测用户会话分布。报告包含准确的事件、增量、紧凑记录及工具计数；提示、回答、推理及工具输出的 UTF-8 总字节数；最大回答大小；标记计数；以及持久化字节大小。每个成功样本必须观察到最后模型增量、回到空闲状态并正常退出。[夹具测试](../tests/performance.spec.ts) 验证确定性重放与失败汇总；[PTY 生命周期测试](../tests/performance-terminal.test.ts) 覆盖输出尾部淘汰后的就绪状态、失败退出、致命信号、取消和超时后的清理。

## 渲染器内存

[渲染器回归测试](../../ui/tests/memory.spec.ts)在堆上限为 192 MiB 的全新 Node 进程中运行已安装的生产版 React 和 Ink。测试在渲染器存活时以及清理后显式触发 GC，再检查内存。输出接收器仅计数并保留末尾 1024 个字符，因此测试捕获不会持有已渲染的历史。

```sh
NODE_ENV=production node --expose-gc --max-old-space-size=192 apps/tui/packages/ui/tests/fixtures/ink-memory.mjs
```

| 字段 | 测量约定 |
|---|---|
| 操作 | 替换一个真实 Ink `Text` 3000 次，每次等待渲染刷新完成；再次显示第一个值并清理。 |
| 工作负载 | 唯一帧标记加 16 KiB 固定的合成工具式文本，在 100 列终端中截断显示。不涉及网络、模型、会话日志或已保存的对话记录。 |
| 内存 | 预热后、每 1000 次更新后及清理后触发 GC。保留堆增长必须低于 16 MiB；耗时不设通过阈值。 |
| 行为 | 最后一次更新及再次访问的文本均到达终端。现有组件和 PTY 场景负责完整应用渲染及终端恢复。 |
| 负向对照 | 未打补丁的 Ink 7.1.1 在前 1000 次更新后便无法通过同一内存断言。 |

2026-09-26 在 Linux x64 和 Node 26.7.0 上采集的[每种实现三个样本](results/ink-cache-memory.json)显示：3000 次更新后的保留堆中位数从打补丁前的 115.7 MiB 降至 16.6 MiB。包含强制 GC 和清理的耗时中位数从 1783 ms 降至 1428 ms。该测试测量渲染器缓存保留量及本地渲染开销，不代表模型延迟，也不对持久会话历史的大小作出限制。每个缓存最多保留 1000 个条目，键和字符串值合计不超过 1,048,576 个 UTF-16 代码单元。单个大值仍可渲染，但不会被缓存。

限制历史重放批次之前，缓存补丁检出还完成了全新、500 回合和 2000 回合历史[各三个构建后配置样本](results/ink-cache-profile-linux.json)，包括流式输出、输入和正常退出。保留堆中位数分别为 54.6、65.0 和 87.5 MiB。2000 回合的 RSS 峰值中位数为 985.2 MiB，表明该实现的重放具有较大的瞬时开销。这些 Linux 结果不应与下方 macOS 历史结果作为修改前后对比。诊断仅在确认子进程成功退出后接受 Bun 1.4.2 的 Linux PTY 关闭状态；存活期间的读取失败、失败退出和信号仍作为错误，由[驱动测试](../tests/performance-terminal.test.ts)覆盖。

## 开发备注

Bun 原生历史对比使用相同的源码哈希、视口和夹具，每种工作负载各采集三个样本：[开发模式](results/bun-native-development.json)和[生产模式](results/bun-native-production.json)。生产构建将插件从 104,323 字节缩小至 58,820 字节。500 回合就绪中位数从 6197 ms 降至 5114 ms（17.5%），RSS 峰值从 909.4 MiB 降至 804.8 MiB（11.5%）。保留堆分别为 58.1 和 56.4 MiB；流式期间输入分别为 2.14 和 2.26 ms，接近 2 ms 的观察间隔。全新会话就绪分别为 1321 和 1281 ms。这些测量支持选择生产版 React，并不意味着 Bun 执行 Harness 更快。[原生驱动的尾部样本](results/bun-native-tail.json) 在 1 GiB 上限下恢复 2000 回合时失败；驱动记录了 Node 的 SIGABRT 和堆耗尽消息。

[Node 24 的单次生产样本](results/bun-native-node24.json) 在 5540 ms 内完成 500 回合恢复，RSS 峰值为 857.5 MiB，流式期间输入观察为 2.27 ms。构建后的重放、导航、附件和终端恢复在 Node 24 与 26 上也均通过。下方较早的 script 驱动测量保留各自的产物和驱动上下文，其样本不与 Bun 原生对比混合汇总。

2026-09-22 在 macOS x64 上采集的本地证据：[Node 26 开发模式](results/node26-development.json)、[Node 26 生产模式](results/node26-production.json)和 [Node 24 开发模式](results/node24-development.json)。JSON 文件保留产物哈希及未经更改的数值样本，省略原生失败堆栈。这些是诊断观察，不是可移植的性能预算。下表每个 Node 26 行均为三个成功样本的中位数；尾部工作负载则报告失败。

### 历史重放测量

当前[历史展示器](../../ui/src/replay.ts)按展示行数、终端行数及文本大小限制各批次；单个超大行可以独立推进。积压历史回放期间，[回滚输出](../../ui/src/scrollback.tsx)等待每次渲染刷新完成后再接收下一批次，并通过一个持续保留的 Ink `Static` 实例保持有序输出。完整历史仍保留在会话中；分批限制展示工作量。对比实现时需使用相同的六种工作负载、种子产物、驱动、运行时及依赖，并分别观察首次输入和完整重放终点。上述历史结果保留各自的原始夹具及测量终点。

[优化前](results/history-replay-before.json)和[优化后](results/history-replay-after.json)各包含六种工作负载的三次成功采样，均于 2026-09-26 在 Linux x64、Node 26.7.0 和 Bun 1.4.2 上测得。两个应用构建使用同一份冻结的源码快照；基线恢复整段历史的 Static 接收方式，并关闭行换行缓存。实际源码哈希仅在 `app.tsx` 和 `line.tsx` 上不同。种子、启动模块、组合配置及锁文件的哈希一致。候选产物与通过 26 个 PTY 场景的已构建应用完全相同。[隔离记录](results/history-replay-comparison.json)还验证了 988 个外部运行时文件保持不变。

| 工作负载 | 首次输入，ms，之前 → 之后 | 完整回放，ms，之前 → 之后 | 峰值 RSS，MiB，之前 → 之后 |
|---|---:|---:|---:|
| `fresh` | 777 → 756 | 777 → 756 | 220.1 → 221.2 |
| `small` | 938 → 879 | 938 → 879 | 230.5 → 236.5 |
| `typical` | 1933 → 1050 | 1933 → 1888 | 428.9 → 331.4 |
| `tail` | 5306 → 1207 | 5306 → 4889 | 986.8 → 377.5 |
| `tools` | 4115 → 1164 | 4115 → 3951 | 804.7 → 365.9 |
| `large-output` | 1274 → 926 | 1274 → 1281 | 324.5 → 270.8 |

2000 轮会话可提前 77% 接收输入，峰值 RSS 降低 62%；完整回放快 8%。工具密集历史可提前 72% 接收输入，峰值 RSS 降低 55%；完整回放快 4%。大回答的完成时间中位数基本不变。新会话和短历史没有同等程度的内存下降。这些是未设置校准时间预算的本地中位数，不包含模型与网络延迟。

在恢复大型历史的工作负载中，回放期间发送的探测输入耗时 87–133 ms，空闲和流式生成时的输入仍约为 35–39 ms。未分批渲染器只有在历史阻塞启动结束后才收到首次探测输入。长历史强制 GC 后的保留堆内存为 87.4 → 81.8 MiB，因此内存改善主要来自临时布局分配。会话状态和保存的终端输出仍随历史增长。大型工作负载的启动输出增加约 3–7%。新会话的首个增量中位耗时从 78.5 增至 103.0 ms，典型历史从 78.4 增至 95.1 ms；这些本地的提交至增量耗时包含合成适配器。

每批最多接收 512 个展示行、1024 个终端行和 128 Ki 个 UTF-16 文本单元；单个超大行可以独占一批。弱引用缓存让测量与渲染共享每个不可变行的位置及换行结果，宽度改变时替换其唯一条目。[探索性采样](results/history-replay-tuning.json)记录了调优时考虑的较小批次；这些采样早于冻结源码对比，不与后者合并统计。

[游标测试](../../ui/tests/replay.test.ts)检查线性遍历、追加顺序、大回答完整性和三种批次边界。[Ink 测试](../../ui/tests/scrollback.spec.tsx)阻塞 stdout 交付，在回放等待时检查输入及取消，然后验证有序输出、终端缩放、会话导航和保留草稿的子会话查看。临时移除全部三种接收边界后，多行回答回归测试会失败，因为全部 1000 行都在首次刷新屏障之前打印；恢复边界后测试通过。203 个定向 Node 测试、17 个 Bun 测试、类型检查、布局检查和 26 个已构建 profile 的 PTY 场景均通过。本次对比不包含真实模型调用或长时间生产会话。
