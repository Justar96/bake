## Subagent design

This is a design for review, not final. It ports Bake 0.3's continuable children (`packages/subagent/*`) onto Pi's session format and this stack's job, notice, and run-control machinery, and adds per-call model choice.

### Goals

- A parent can start a child on **any available model** and thinking level, or inherit its own.
- Communication between parent and child is **clean and clear**:
  - every exchange has one kind, one sender, and one recipient;
  - it is written to the recipient's log before it takes effect;
  - it is delivered by fixed rules and is never hidden state.
- Children are **owned**: the parent's shutdown stops and awaits them, and none outlives its process.
- Restart is **honest**: nothing is re-run, every unfinished run is reported once, and a saved child can still be continued.

### Model-visible tools

The descriptions and result texts are Bake 0.3's, verbatim, except where marked **(Bake addition)**.

| Tool | Who has it | Arguments | Result |
|---|---|---|---|
| `subagent` | parent (depth 0) | `description` (3–5 words), `prompt` (standalone), `run_in_background` (default true), `provider`, `model`, `reasoning_effort` (all three optional) | background: `started subagent {id}`; foreground: the child's closing text |
| `list_subagent_models` | parent | `provider`, `model` (both optional) | providers; that provider's models; or one model and its thinking levels (0.3 `list-models.ts` text) |
| `send_message` | parent and child | `agent_id`, `message` | `message delivered to agent {id}` |
| `interrupt_agent` | parent | `agent_id` | `interrupt requested for agent {id}` |
| `list_agents` | parent | `scope` (`children` or `descendants`; with depth 1 the two are the same) | `{id} [{status}] — {label} · {provider}/{model}` per row **(Bake addition: the route)**, or `(no subagents)` |

- **Depth:** the maximum is 1, as in 0.3. A child gets the parent's tools minus `subagent`, `list_subagent_models`, `interrupt_agent`, and `list_agents`, and keeps `send_message` to reach its parent.
- **Permissions:** a child inherits the parent's sandbox mode, approval policy, plugins, and MCP servers.
- **Visibility:** the model-selection arguments and `list_subagent_models` are always shown when more than one model is available. In 0.3 they sat behind a setting. This changes what the model sees, so it needs a D-number and the paired eval.

### Model selection

- **Choices** are `ModelRuntime::snapshot().available()`: models with credentials, the CLIProxyAPI route included. An optional setting, `subagents.models` (patterns in the style of Pi's `enabledModels`), narrows the list. The default allows every available model.
- **Resolution** happens before anything is created, so a refused call writes no file and starts nothing:
  - All three arguments omitted: the child uses the parent's current model and thinking level.
  - `provider` and `model` go together. One without the other is an error, using 0.3's text.
  - A route that is unknown, unavailable, or not allowed is an error that names the allowed routes (0.3 `model-selection.ts` wording).
  - A route given without `reasoning_effort` gets the new model's default level. A `reasoning_effort` the model does not support is an error listing the supported levels (`available_thinking_levels`).
- **Recording:** the child's file starts with Pi's `model_change` and `thinking_level_change` entries, so a resumed or continued child keeps its route. The parent's `subagent` tool result details record `{agentId, label, file, provider, model, thinkingLevel}`, and `list_agents` reads them.
- **Credentials:** the child uses the parent's `AuthStorage` and `ModelRuntime`. No key is copied into the child's file or the details.
- **The task router** (0.3 `auto-route.ts`, which picks a route when the model gives none) comes in a later PR. It must keep the default route when the router is unset, slow, or failing.

### Intercom

Each kind is a different entry type, so a transcript never credits one agent with another's words or with the runtime's account (0.3's rationale in `continuation-messages.ts`).

| Kind | Direction | How it is sent | Entry in the recipient's file | Text the recipient's model sees |
|---|---|---|---|---|
| Task | parent → child | `subagent` | the child's first user message | the prompt, then 0.3's return guidance naming the parent id and how to `send_message` it |
| Message | parent → child, or child → its parent | `send_message` | `custom_message`, `customType: bake.agent.message`, details `{messageId, from, to}` | `Agent {from} sent a message: {message}` |
| Settlement | runtime → parent | a child run ends | `custom_message`, `customType: bake.subagent.notice`, details `{agentId, runId, stopReason}` | 0.3 summary by stop reason, then `Its closing message:` and the text, or `It left no closing message.` |
| Interrupt | parent → child | `interrupt_agent` | none; the run aborts and its settlement says it `was stopped before it finished.` | |
| Lost run | runtime → parent, after a restart | recovery | `bake.subagent.notice` with `stopReason: interrupted` **(Bake addition)** | `Background subagent {id} was interrupted when Bake stopped and did not finish. Send it a message to continue it.` |

Delivery rules, the same for every recipient:

1. **Log first.** A message is written to the recipient's file before `send_message` returns. "Delivered" means durably queued for the recipient, not read. There is no reply channel: an answer is another `send_message`.
2. **A busy recipient** gets it as a steer at its next step, as job notices do in a run.
3. **An idle recipient** gets a new turn.
   - A resident child resumes in place. A saved child that is not resident is cold-resumed from its file.
   - A parent turn opened by child traffic spends the parent's wake budget (`MAX_CONSECUTIVE_WAKES`, shared with job notices). Past the budget, traffic waits for the next user prompt, which carries it ahead of the user's text.
4. **Order.** Messages are FIFO from each sender to each recipient. `messageId` is the entry id, so retries and recovery never deliver twice.
5. **Adjacency.** A child can message only its parent; a parent, only its direct children. Any other id is an error that names `list_agents`. Messages are capped in size (suggested 64 KiB), and an oversized one is refused before writing.
6. **Settlement is exactly once per run.** A child's run ends once (`runId`); its notice is claimed once and written once. Settlement shares the job-notice delivery path, so print mode, the TUI's idle turns, and the wake budget all apply. A child is not a job (`job_*` does not list it). Its notice uses the same claim, wake, and delivery code.
7. **Sending a message does not end the sender's turn.**

The terminal shows a settlement as an information row, and a message as `← agent {id}: {first line}` or `→ agent {id}: {first line}` (0.3 `presentation.ts` keeps titles to the first line, 48 characters). A child's full transcript is its own session file; a viewer is later work.

### Lifecycle and ownership

- **States** (as in 0.3 `list_agents`):
  - `running`: a run is in progress;
  - `idle`: resident, between runs;
  - `ready`: saved in its file, not resident.
- **Transitions:**
  - starting a child, or a message to an idle or ready child, makes it `running`;
  - a settled run makes it `idle`;
  - eviction, or the parent's exit, makes it `ready`.
- **Ownership:**
  - Each child is an `AgentSession` over its own `SessionManager`, built by the same composition as the parent (`cli/mod.rs`) with the reduced tool list.
  - Its runs are tasks under the parent's `WorkGate`, so parent shutdown cancels them, awaits their cleanup, closes each child's writer, and releases its lock.
  - Limits: concurrent running children are bounded, matching 0.3's limits; check `packages/subagent/subagent`.
- **Storage:**
  - The child file sits in the parent's sessions directory, with header `parentSession` set to the parent's file (Pi's link).
  - The child id is the child's session id.
  - `/resume` lists child sessions under their parent, or hides them; decide in the TUI PR.
- **Restart:**
  - The parent's entries are the source of truth: child creations come from `subagent` results, settlements from notices.
  - A run started on the current branch with no settlement gets one lost-run notice with the next prompt and is never re-run.
  - The child stays `ready` and continuable.
  - A missing or unreadable child file appears in `list_agents` as `{id} [diagnostic: unavailable]` (0.3 diagnostic rows).
- **Print mode:** `bake-rs -p` waits for running children and their notice turns within the existing 10-minute bound, then interrupts what remains and reports the count, as for jobs.
- **Approvals:**
  - A child inherits the policy.
  - In the terminal, its approval prompt goes to the same broker, labelled with the child's id and label.
  - In print mode, approvals are disabled, as for the parent.

### Proofs to write

- **Resolution:** model resolution accepts and refuses each argument form, writes nothing on a refusal, and the chosen route reaches the child's first request and its file.
- **Delivery:** for messages and settlements in both directions, a busy recipient gets a steer at its next step, an idle one gets a new turn, past the wake budget delivery waits for the prompt, ordering holds, and nothing is delivered twice.
- **Settlement races:** barriers place a child's settlement before, during, and after the parent's run and shutdown. Each case admits exactly one notice and leaves no orphan task or process (roadmap scope 11).
- **Restart:**
  - kill the parent mid-child run, resume, and see one lost-run notice;
  - `send_message` continues the child from its file;
  - nothing is re-run.
- **Adjacency and limits:** non-adjacent ids, unknown ids, oversized messages, and depth 2 (no `subagent` tool in children) are refused.
- **End to end:** the built binary with `-p` and the PTY suite, with live scenarios over the loopback model server using two models, so the route can be seen per request.

## Machine-specific notes

The earlier machine used these. Adapt them on the new one.

- **macOS:** `bun run preflight:mac` uses SSH host alias `macpro` (`~/.ssh/config`, key login; Intel x86_64). From WSL, SSH works only through the Windows OpenSSH binaries: put a `ssh` symlink to `/mnt/c/Windows/System32/OpenSSH/ssh.exe` and an `scp` wrapper that converts paths with `wslpath -w` into a directory, then prepend it to PATH. On the Mac, a real `rg` is at `~/.local/bin/rg` and cargo-about is at `$HOME/bake-ci-native-licenses-20261017/tools/bin/cargo-about`. Native run:
  `bun run preflight:mac 'BAKE_CARGO_ABOUT=$HOME/bake-ci-native-licenses-20261017/tools/bin/cargo-about bun run preflight --only native'`
- **Windows:** the earlier machine used a checkout at `C:\Users\<user>\bake-ci`, synced with `git fetch \\wsl.localhost\Ubuntu\<repo> <branch>`. Worktrees cannot be fetched over UNC, so fetch from the main repository. `.preflight/run-pty.ps1 -Filter <name>` built `bake-cli` and `bake-tui` and ran `bun run test:rust:pty`.
- **Windows input probe:** to read raw console records under ConPTY, run a PowerShell `ReadConsoleInputW` P/Invoke script through the `ConPty` class in `scripts/rust-pty-conpty.ts`. That is how the Alt-code sequences were confirmed.
