# Scope 00: product support decisions and acceptance matrix

## Summary

This page lists what Bake ships today, what the Rust 0.4 line must preserve, and which questions only the product owner can answer. The inventory comes from source at `origin/develop` `ae5eb51ab6` and the `v0.3.8` tag `dcb26d756e`, read on 2026-10-07. It belongs to [scope 00](README.md) of the [Rust migration roadmap](../README.md).

Since [D22](#decision-register), Pi is the primary port source and Bake's TypeScript runtime a selective reference. The owner retained the CLIProxyAPI provider route, reading existing Session logs, Session format 3 for new writes, and the model-visible surface; [D32](#decision-register) later narrowed the retained contracts to the CLIProxyAPI route, Bake's sandbox and permissions, and the `~/.bake` home. The inventory below records what 0.3 ships so each behavior can be kept, replaced by Pi's, or retired by decision; it is no longer a parity target by default. The approved exceptions are the Node/TypeScript runtime and custom JavaScript/Cordis profiles: 0.4 ships Rust only and excludes those profiles, with no compatibility runtime or profile migration deliverable ([D5](#decision-register)). 0.4.0 must also ship a native plugin API ([D6](#decision-register)). On 2026-10-17 the owner bounded 0.4.0 further: CLIProxyAPI is its only provider route ([D8](#decision-register)), Bake Desktop integration is deferred beyond it ([D9](#decision-register)), and the Cordis-specific tooling is retired in favor of Rust-native inspection and management capabilities that are still to be designed ([D7](#decision-register)). The shipped-surface tables keep describing 0.3 as it ships; only their 0.4 disposition columns carry these decisions. This page tests nothing; isolated qualification probes do not constitute a native implementation. Provider, platform, and plugin rows say what evidence is missing; none claims native parity.

## How to read decisions

Active decisions use the three classes below. A row marked settled or superseded links to the later owner decision that governs it.

| Class | Meaning | Who can change it |
|---|---|---|
| **Decided by request** | The current user request or a repository instruction already settles it | The user, through a new request |
| **Scope-00 default** | A conservative default adopted here so work can continue; it preserves current behavior | The product owner, through a reviewed change to this page |
| **Owner decision** | A recommendation that changes support, release routing, or packaging; it is not in force until the owner approves it | The product owner only |

### Provider routes and authentication

Bake routes every model request through [`bake-llm-pi-ai`](../../../../packages/llm/llm-pi-ai/README.md) over `@earendil-works/pi-ai` 1.0.0, pinned in `bun.lock`. There are two route kinds, and the Rust port must keep them apart.

**Authentication.** Each route resolves an API key reference per request through the credential store: environment first, then the managed `$BAKE_HOME/.credentials.yaml`, then project and user `.env` files ([credentials](../../../../packages/credentials/credentials-local/src/index.ts)). **0.4.0 bounds ([D8](#decision-register), decided 2026-10-17).**

- **Required:** the CLIProxyAPI route as the [retained contract](../pi-first-plan.md#retained-contracts) describes it, over the three generic protocols it selects per model, with its key resolution, login, refresh, and logout. Each protocol needs sanitized wire fixtures, and the route needs a live smoke test against a proxy.
- **Deferred to a later release:** `deepseek-official`, the catalog APIs outside the generic three, and the direct API-key and OAuth logins listed above. 0.4.0 qualifies and claims none of them. Scope 07 states how 0.4.0 presents such a route; it never re-routes one silently, and no Node fallback exists ([D5](#decision-register)).
- No route is claimed as qualified until its own fixtures and smoke tests pass. Missing credentials are recorded as missing evidence.

### Windows confinement

On 2026-10-17 the owner selected **AppContainer with explicit read and network grants** for Rust 0.4 Windows confined modes. D24 therefore permits reads and network access to be restricted on Windows. Permission presets and approval requirements remain, and a requested confined command must fail before launch if its grants or isolation cannot be established; there is no unconfined fallback. The `danger-full-access` mode remains an explicit permission choice.

The [native mechanism probe](https://github.com/Justar96/bake/actions/runs/39015328291) at `ee64b98983b802c49e5c705e91d73a10ba6ca4b4` ran on Windows build 10.0.26100.33438. The write-restricted token allowed outside deletion and source-side rename. Low integrity blocked those medium-integrity effects but still allowed deletion in another low-integrity workspace. AppContainer denied the tested outside deletion, rename, and cross-workspace deletion while allowing workspace creation and deletion. It denied the tested outside read; its loopback connection timed out. That timeout does not prove a network denial rule. These are mechanism observations, not qualification of a production backend.

Scope 04 must implement the AppContainer runner, explicit read-path and network grants, and owned process-tree teardown. Scope 12 must use the same policy for local MCP servers and hook processes. Qualification must exercise allowed and denied operations through the real runner, executable and runtime dependencies, file and parent-directory deletion rights, rename in both directions, links and junctions, other workspaces, descendants, and failure cleanup. Network tests must distinguish deliberate denial from an unavailable destination, and cover granted and denied remote and loopback access. Any required privileged host setup must be made explicit; this choice does not authorize hidden elevation or broad host permission changes. Until that evidence passes, the native default continues to refuse Windows confinement.

### Packaging, update, and rollback

The shipped 0.3 archive contains the Node launcher. Its [installers](../../../../distribution/README.md) require Node 24 and its [updater](../../../../packages/boot/updater/src/verify.ts) checks `apps/cli/lib/bin.js` with Node before switching the installed release. These describe the TypeScript install; [D32](#decision-register) excludes upgrading it to Rust.

Scope 16 qualifies these native obligations:

1. Install a Rust-only archive on a host without Node. A fresh install beside 0.3 leaves that install, its data, and its existing command links working.
2. Verify signed native manifests and archives, launch-check the candidate, and update or roll back between 0.4 releases atomically. Test each supported native data-format boundary; a successful executable switch alone does not establish usable data.
3. Preserve user-owned aliases and prevent the installer from taking a command link owned by another install.
4. Keep TypeScript and Rust publication routes separate. The existing 0.3 `latest.json` route must not serve Rust archives to its updater. A 0.3 publication cannot replace a native stable manifest, a publication cannot move a channel to an older version, and D13 forbids new 0.3 publication after 0.4.0 ships.

A local, host-only preview of the native archive layout and its self-check exists ([distribution](../../../../distribution/README.md#native-preview-archive)); it is unsigned, unpublished, and not yet a release layout, since it lacks the Cargo dependencies' license texts. Signing, installation, publication routes, update and rollback, and the five-platform rehearsal still need implementation and tests. No preparatory TypeScript-to-Rust updater or shared Session-format compatibility layer is required.

## Profile support and native extension strategy

[D5](#decision-register) excludes custom JavaScript/Cordis profiles from 0.4.0. The release does not provide a compatibility loader, translator, or a migration project for those profiles. [D6](#decision-register) requires a native plugin API. [D7](#decision-register) retires the shipped Cordis tooling and requires Rust-native inspection and management capabilities in its place. TypeScript remains a development oracle; no shipped command selects it.

**Native profile boundary.** Scope 05 translates shipped bundle behavior into typed native configuration. Pin shipped expressions in comparison fixtures; the Rust launcher does not interpret Cordis compositions or executable YAML. Requests to load, create, or install into a custom JavaScript/Cordis profile must fail before profile code, package scripts, an agent, or a configuration write runs. Report the unsupported profile and its source; leave its files unchanged. A custom profile is excluded even if its rows happen to match shipped rows. Retained `tui` and `headless` profiles remain configurable through typed native settings and overlays, including MCP server definitions and hook-process configuration. Scope 05 defines their schema and the mapping of launcher flags; compatibility applies to retained values and precedence, not to loading legacy `cordis.patch.yml`. `--patch` accepts only the defined native schema, with no package rows, module resolution, or executable expressions. Native configuration and the plugin API receive their own documented interfaces. `--dump-config` and `--self-check` follow the same boundary.

**Existing built-in profile directories.** A nonempty legacy `cordis.patch.yml` must cause native startup to refuse with the path and a diagnostic explaining that its settings need to be entered in native configuration. Do not execute, import, rewrite, or silently ignore its entries, even when they configure only MCP, hooks, or session search. Empty and comment-only layers may be treated as unconfigured after non-executing format validation; malformed layers refuse. Scope 05 defines the native configuration location and a deliberate way to select it without overwriting the legacy files. A custom profile or Cordis user preset remains excluded even if its layer is empty.

**Boundaries that hold regardless of implementation:**

- **Native code cannot transparently host arbitrary Cordis JavaScript.** Cordis plugins depend on scoped services, waterfall events, the Loader, and in-process module identity. A JSON-RPC shim around individual plugins would not reproduce those semantics. Custom JavaScript/Cordis plugins are outside the native support target. Authors may write new native extensions once its API exists; Bake does not promise to convert their old plugins.
- **The Electron utility process needs integration work.** Bake Desktop can deliver messages through `process.parentPort`, which exists only inside an Electron utility process running JavaScript. A native executable cannot be that process. Desktop integration is deferred beyond 0.4.0 ([D9](#decision-register)); a later release that takes it up needs a path the Desktop maintainers approve and a test against the real Desktop consumer.
- **Code mode stays JavaScript.** `run_code` executes model-written TypeScript in a confined QuickJS VM ([codemode](../../../../packages/ptc-runtime/ptc-runtime-codemode/README.md)). A native host embeds an equivalent confined engine. It does not change the language the model writes.
- **Development comparison.** Work that runs in the TypeScript runtime never closes a native scope. A native profile never delegates to it.

**Native extension surfaces in 0.4.0 ([D6](#decision-register)):** MCP servers (stdio and Streamable HTTP) and hook processes stay supported. They do not satisfy the plugin API requirement on their own. 0.4.0 must also ship a native plugin API. The [native design](../native-plugins.md) owns the implementation status. Scope 12 must implement and qualify:

- the protocol or ABI, including whether plugins run in process or out of process;
- which contributions a plugin can make;
- permissions, and how plugin effects pass the same approval and sandbox rules as built-ins;
- lifetimes, including failure and a shutdown that awaits owned work;
- versioning and compatibility rules;
- the inspection and management capabilities that replace the retired Cordis tooling ([D7](#decision-register)): what a user or the model can list, query, enable, disable, or diagnose, and through which surface;
- proof through at least one named consumer exercised against the real native runtime.

Any model-visible catalog for the API must be generated from its real interface, never from the Cordis API catalog. The API does not migrate Cordis/JavaScript plugins. Design text and a partial API do not establish the full consumer and management qualification.

## Release lines and support window

[D34](#decision-register) and [AGENTS](../../../../AGENTS.md#branches-and-releases) define the branch policy already in force. Rust changes target `develop`. Its next release is 0.4.0 through a merge-commit PR to `main`. TypeScript bug and security fixes target `release/0.3` and publish 0.3 tags there. Nothing from `release/0.3` merges into `develop` or `main`; a relevant Rust fix is ported separately with its own tests.

Scope 16 must implement separate publication routes before publishing Rust archives. Existing 0.3 updaters read the signed `latest.json` route and must remain on TypeScript under D32. A native manifest, signing, installer, and update/rollback tests must establish the Rust route without sending a Rust archive to those updaters. The manifest paths and channel enforcement remain design and qualification work; the maintenance branch does not prove them.

**Support window.** Under D13, Bake's maintainers provide 0.3 bug and security fixes only until 0.4.0 ships. That release ends TypeScript maintenance and supported legacy `dsh`, profile, and package aliases (D10); only Rust Bake is shipped and maintained afterwards. The 0.4.0 release notes must announce end of support and explain the separate Rust installation. Retirement does not delete existing installs, user-owned command links, or frozen evidence. The existing 0.3 update route must remain pinned to its final TypeScript release, and scope 16 must prevent later 0.3 publication or routing a Rust archive to it. The proposed 90-day/0.4.2 extension is not adopted.

## Incremental delivery under the develop to main rule

Every Rust change starts from current `origin/develop` on its own branch and targets `develop`, with dependent changes using GitHub’s official PR stacks. Qualification governs when the Rust release can be prepared; the completed port does not authorize a tag or publication.

Until scope 17 removes it, the frozen TypeScript agent still builds and its relevant gates pass. Native development does not change the 0.3 launcher’s default or add the preview to 0.3 archives. A 0.3 hotfix goes through `release/0.3`, not through the Rust-first `develop` branch. Scope 17 checks consumers before removing TypeScript product code, preserves frozen evidence, and qualifies the final Rust-only artifacts.

## Native consumer coverage gaps

These consumers or behaviors have no test that a native implementation could be checked against today:

- **Bake Desktop:** the external app, its Electron utility-process launch, and its pinned protocol copy. Deferred beyond 0.4.0 ([D9](#decision-register)), so this gap does not block 0.4.0; access to that checkout is a dependency of any later Desktop work.
- **Excluded custom profiles:** native entry-path refusal fixtures are missing. They must prove that custom Cordis profiles, executable YAML, and npm package scripts never execute or change files; third-party migration is outside the target ([D5](#decision-register)).
- **Catalog providers:** no live smoke tests and no per-family wire fixtures for the ten non-generic API families. pi-ai's nine OAuth providers have no recorded flows. Bedrock and Vertex authentication goes through their SDKs and has not been inventoried per provider. These routes are deferred beyond 0.4.0 ([D8](#decision-register)), so these gaps do not block it.
- **Windows sandbox:** the retained `WRITE_RESTRICTED` mechanism permits deletion and moving an outside file into the workspace on the tested native host. The default provider refuses confinement. The owner selected AppContainer with explicit read/network grants; its production runner and grant policy must be implemented and qualified before Windows can be enabled ([Windows contract](#windows-confinement)).
- **Windows terminal:** the PTY driver is POSIX-only, and no ConPTY scenario exists.
- **Old updaters:** no test runs a released 0.3 updater against a changed archive layout.
- **Retained `api`, `client`, `host`, and `typert` packages:** `bake-typert-registry`, `bake-typert-loader`, and `bake-api-gateway` are composed in the base bundle. Their consumers, including the `sessionFeedback` Host Remote, have not been traced.
- **Terminal setup:** edits to external terminal configuration files have no cross-runtime test.
- **Native plugin API:** the [native design](../native-plugins.md) proposes a `guard` consumer and inspection and management capabilities ([D6](#decision-register), [D7](#decision-register)); no implementation or consumer evidence exists yet.
- **`bake plugin`:** depends on pnpm being installed on the host and installs JavaScript plugins that 0.4 cannot run. It is retired in 0.4 ([D7](#decision-register)); any native management command is part of the scope 12 design.
- **Platform minimums:** no recorded minimum OS, kernel, glibc, or macOS deployment target.
- **Performance:** the instrumentation is Node-specific, and several interactive workloads are excluded.
