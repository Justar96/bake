# Durable execution direction for the Rust harness

## Summary

Shape the native runtime so that every unit of agent work (a model request, a tool call, a compaction, a child agent, a background job) is an owned, typed task whose start, progress, and outcome are recoverable from the session file. This page takes the task-and-scheduler model of Pi Durable as a design reference and applies it inside Bake's retained contracts: Pi's session format ([D32](scope-00/support.md#decision-register)), one serialized owner per agent, and model requests reconstructable from the session file. It adds internal structure and crash-recovery proofs to scopes 02 to 13. The owner adopted selected-run recovery, typed task documents, and background compaction as [opt-in 0.4.0 features](#opt-in-features-for-040) under [D37](scope-00/support.md#decision-register); implementation and qualification are tracked below; release acceptance still requires crash evidence and paired evals. Other model-visible changes remain post-0.4.0 candidates.

**Status: partially implemented, under qualification, 2026-10-18.** The direction follows [D22](scope-00/support.md#decision-register), [D32](scope-00/support.md#decision-register), [D33](scope-00/support.md#decision-register), and the opt-in adoption in [D37](scope-00/support.md#decision-register). The rules below remain requirements for the native runtime; the evidence covers the named properties, not the full release. [Current implementation](#current-implementation) says which already hold in `bake-rs` and which test, if any, shows it; [Crash-recovery matrix](#crash-recovery-matrix) marks each kill point's evidence. The support register owns the adopted scope; this page specifies its required behavior and missing evidence. Bake Session format 3 and its events (`tool/call`, `assistant/attempt`, `compaction/start`, and the rest) are not written or read by 0.4; where this page names them, it describes 0.3. Pi Durable's storage, API, and entry kinds are not adopted.

The comparison's central point applies directly to Bake. A session-based harness persists the conversation, but the work in flight lives in process memory: after a crash the harness can show what happened, yet it cannot tell which work was unfinished or whether repeating it is safe. Pi Durable persists execution state too, so a new process can find unfinished work and continue it. ## What 0.3 recorded and what Pi's session records

Bake 0.3 was closer to durable execution than a typical session harness. Under [D32](scope-00/support.md#decision-register) its Session events are not carried forward, but the properties they gave are obligations the native runtime keeps inside Pi's format. Pi's session file holds one JSON line per entry, linked by `id` and `parentId`: `message` entries (user, assistant with its `toolCall` blocks, and `toolResult` messages), `compaction` and `branch_summary` entries, model and thinking-level changes, labels, session info, context edits, and `custom` entries that never reach the model.

| Concern | Bake 0.3 | Pi's session in `bake-rs` | Gap the native design closes |
|---|---|---|---|
| Tool intent before effect | `tool/call` logged before dispatch; [crash repair](../../../packages/core/session/src/repair.ts) closed an unmatched call with `TOOL_NOT_STARTED` or `TOOL_OUTCOME_UNKNOWN` | In a persisted session, the assistant `message` holding the `toolCall` blocks is appended and synced before its tools run; if that append fails, the agent is aborted and tool preparation, which checks the abort first, runs no tool. No entry records that a call started. When the next request is built, Pi's `transformMessages` answers a call with no `toolResult` with a synthetic error result, `No result provided`, in the request only; the file is not changed. An assistant message that ended in an error or abort is dropped from the request with its calls | No started/not-started distinction and no replay class, so neither the runtime nor the model can tell whether an effect happened |
| Interrupted turns | Synthetic closers ended the open step and turn | The file ends at the last synced entry; the next request is rebuilt from the path to the leaf | An interrupted run does not continue unless the user resubmits |
| Partial model output | `assistant/attempt` recorded an attempt's stream | An assistant message is appended only at its end, including one that ended in an error or abort; a failed attempt Pi retries stays in the file and is omitted from context by a context edit | A crash mid-stream loses the partial output; scope 06 defines what reaches the file |
| Compaction | `compaction/start` to `compaction/end` logged | A `compaction` entry is appended once its summary exists | The summary runs on the agent's critical path |
| Child agents | `subagent/catalog` and descriptors logged | Not implemented | Scope 11 decides which child state survives a restart |
| Background jobs | [`jobs-local`](../../../packages/jobs/README.md) ran them in-process | Not implemented | Jobs do not survive the process |
| Decisions | Approvals and hook decisions were logged before their effects | The session's permission settings are `bake.permission` custom entries; print mode has no answerer, so escalations are refused and nothing is asked | Interactive approvals and their logged decisions are not implemented |
| UI state | The terminal rendered authoritative projections ([analysis](analysis.md#execution-and-ownership)) | The terminal preview has no agent connection | The native transport should make the projection the only thing a client attaches to |

## Design rules for 0.4.0

These rules define the baseline internal structure and Pi-format behavior. The separately adopted opt-in features add model-visible policy under D37. Each rule is testable through the matrix below.

### 1. Work is an owned task with a recoverable status

Model the runtime's work as typed tasks with explicit states: *pending* (admitted but not started), *running*, *waiting* (on named child tasks, with an all-settled or fail-fast policy), *completing* (outcome decided, owned work still draining), and *terminal* (completed, failed, or aborted). In Rust these are values held by the agent's single owner task, not free-floating futures; each running task has one `JoinHandle` and one cancellation token derived from its owner.

The durable footprint of a task is the session entries the runtime already writes. A task's recovered status must be derivable from the file alone: a `toolCall` on the path to the leaf without a matching `toolResult` is an unfinished tool task, and so on. Scope 02 defines this derivation as a pure projection beside the context rebuild; the projection, not process memory, answers "what was unfinished".

### 2. Record intent before effect, and classify replay

Keep the order: persist the assistant message that requests a call before any effect, and persist the result before the next request uses it. Give every native tool an internal replay class:

| Class | Meaning | 0.4.0 recovery |
|---|---|---|
| `safe` | Rerunning has no external effect beyond the first run (read, glob, search, fetch) | Pi's synthetic error result in the next request; no automatic rerun |
| `idempotent` | Rerunning with the same key has the same effect (a write of identical bytes, a child lookup by owner) | Pi's synthetic error result; no automatic rerun |
| `report` | Effects may have happened and repeating could duplicate them (shell, edits with relative changes, external deploys) | Pi's synthetic error result; no automatic rerun |

The baseline keeps the class as internal metadata. D37 allows selected-run continuation from safe checkpoints, with no automatic replay of uncertain external effects; automatic tool rerun remains a separate [post-0.4.0 candidate](#post-040-candidates). The native plugin API ([D6](scope-00/support.md#decision-register)) requires every contributed tool to declare a class and defaults to `report`. MCP tools default to `report`, matching the [Pi reference](pi-reference.md#native-mcp-direction) rule against retrying calls whose outcome is uncertain.

### 3. One ownership tree, with an explicit background boundary

Agents, turns, model requests, tool calls, processes, child agents, jobs, and timers form one tree. Aborting a node aborts what it owns bottom-up, and a node becomes terminal only after its owned work has finished, so each owner undoes or reports its own effects before its parent proceeds. This is the [defensive patterns](../../defensive-patterns.md) obligation made structural.

Mark the boundary between foreground and background work explicitly. Foreground work belongs to the current turn: the agent is idle only once it is done, and Esc cancels it. Background work (a job, a scheduled follow-up, a detached child) belongs to the agent but not the turn: the turn can end while it runs, an ordinary cancel leaves it alone, and only disposing the agent or cancelling that node stops it. Scope 11 maps each Bake surface it ports (Esc during a child call, job kill, goal continuation) onto this tree and states each observable outcome.

### 4. Commit related entries as a recoverable group

Pi's format appends entries one line at a time, so a crash can leave any prefix of a group that belongs together (a tool result and the context it adds, an inbox claim and its user message, a goal change and the entry that caused it). The native writer exposes a group append that writes a group in order, and the owner publishes no view until the group is written. Loading must handle every prefix of every group. Scope 03 enumerates the groups and tests a crash after each line. True all-or-nothing commits would need a format change and stay out of 0.4.0.

`SessionManager::append_group` is that writer. It takes typed `GroupEntry` values, each the entry its single append writes with the same checks; there is no raw-JSON entry and no callback into the manager. The group's semantics:

- **Checks first.** Every entry is built and checked before anything is written. A failed check (a context edit's target missing, off the active branch, or not editable) returns its error and changes nothing in memory or on disk. Recovery omission treats a failed check as a session gap and stops later writes and requests, even though the group wrote nothing.
- **Order and exclusion.** The entries are chained (the first a child of the leaf, each later one a child of the one before) and written while the caller holds the manager: in `AgentSession`, under the session lock at the write boundary, so no other entry lands between them and no caller reading through that manager or under that lock sees part of the group. The writer lock excludes other writers, not readers: another process reading the file meanwhile sees whatever prefix has reached it.
- **Line by line.** From one open of the file, each line is written and then synced before the next. A session whose file is not due yet writes nothing, as for every append; one whose file is due creates it with the entries before the group, then appends the group.
- **Not atomic.** A crash leaves any prefix of the group, possibly ending in a torn line, which loads as Pi's loader reads any file. A torn line whose whole JSON reached the file reads as its entry.
- **Failure before the first line** (writer lock held or closed, file not creatable): an error other than `SessionError::GroupWrite`; nothing of the group is written or kept in memory.
- **Failure at a line**: `SessionError::GroupWrite` (`GroupWriteError`) names the entries written and synced, which the manager keeps with the leaf on the last of them, and says what happened to the next line (`FailedLine`): `NotWritten`, `Torn` (some of its bytes are in the file), or `Unsynced` (all its bytes were written but the sync failed, so a reader may see the line now and a crash may lose it). No later line is written. Unlike a single append, which keeps a failed entry in memory as Pi does, the manager keeps only the known synced prefix. That is not always what an immediate reopen reads: an `Unsynced` line, or a `Torn` one whose whole JSON reached the file, reads as one entry more, and a crash may still lose it. Owners show the known synced prefix and halt; nothing reconciles the two views within the run.
- **No retry.** A failed group is never written again: the file may hold its prefix, and a second copy would follow it under new ids. `AgentSession` records the failure as the session's gap at the write boundary, so nothing more is written, the running turn stops, and later prompts are refused.

| Group | Consumer | Entries, in order | On a failed write |
|---|---|---|---|
| Model switch | `AgentSession::set_model` | `model_change`, then `thinking_level_change` when the level changes | Nothing applied unless the model line is known synced; then the new model with the previous level clamped to it. The session stops. A reopen projects the same only when the level line is unreadable; an unsynced or whole-JSON torn level line reads as the new level |
| Recovery omission | `Core::omit_recovery_attempt` (retry and overflow recovery) | A `context_edit` per tool result of the failed attempt, then the attempt's | The transcript is refreshed to the edits known synced, and the failure ends the run before another provider request (no retry wait, no compaction); the session stops. Pi writes the attempt's edit first; Bake writes it last, so no prefix leaves a tool result whose call is omitted, which a provider refuses. The written group projects as Pi's order does |
| New session's model and level | `AgentSession::create` | `model_change` when there is a model, then `thinking_level_change` | Creation fails. A new session's file is created with these entries and its first message in one write; only a file already written without a conversation appends them as a group |

Not groups: a compaction is one entry, its usage inside it; a message, a session name, a thinking-level change alone, and a label are single entries. Future groups use the same API with a new `GroupEntry` kind: a tool result and the context it adds, an inbox claim and its user message, a goal change and the entry that caused it, and plugin entries under the D6 plugin API. Each needs its own prefix analysis, as the omission's order shows.

### 5. Compaction is a task, not a phase of the loop

Implement compaction as a task owned by the agent, with its own cancellation, retries, usage accounting, and recovered status, instead of a step the loop calls inline. The default loop still waits where Pi waits. D37 adds opt-in background summarization with validation and commit at a turn boundary; synchronous overflow recovery remains available.

### 6. Clients attach to the owner's view

The agent owner publishes one view: transcript projection, live stream, running tasks and their output, inbox, usage, and context pressure. The TUI, headless output, and any retained transport client each take the current view, then deltas; a client that joins late or reconnects starts from the current view and receives no replay of missed deltas. A slow client's queue is bounded and collapses to the newest full view. This makes the existing "render projections, keep no competing copy" rule a transport property, and gives scope 15's child inspection the same mechanism as the main agent.

### 7. Decisions are recorded once

Any human or hook decision that gates an effect, such as an approval, a question answer, or a hook's block or rewrite, is committed before the effect it gates. Recovery reads the recorded decision as evidence of the original effect. A new or resumed dispatch still checks current permissions and never inherits a one-time approval from another execution. Scopes 04, 08, and 12 choose how each decision is recorded in the session file before its effect; the session's permission settings already use `bake.permission` custom entries, which the model does not see.

## Opt-in features for 0.4.0

**Accepted scope, implementation under qualification (2026-10-18, [D37](scope-00/support.md#decision-register)).** The owner adopted all three features for 0.4.0 with opt-in activation and the qualification gates below. Preserve the Pi loop. All three share the native run control. Explicitly recoverable intervals additionally use a versioned run journal in Pi `custom` entries: run identity, admission, limits, provider-call debits, effect dispatch, and terminal outcome. In a recoverable interval, a debit is synced before a provider call starts and is retained after a crash even if usage is unknown. Enabling task documents or background compaction alone does not make an ordinary run resumable. Normal requests, retry attempts exposed at the model-call boundary, and both summaries of a split-turn compaction share the allowance. A host that executes verification must use the same owned run and limits; the current evidence SDK records host-supplied results and does not execute or budget a verifier itself. HTTP transport retries need their own accounting if a wire-request cap is promised. A deadline cancels execution and stops admission, then awaits cleanup. Separate cleanup-duration telemetry remains a qualification requirement; current live records report total elapsed time. Across a restart, expiry never extends automatically: retain the original deadline constraint and refuse continuation when clock continuity cannot be established. The current implementation refuses every interrupted timed run; it does not infer clock continuity from wall time. An in-process timer uses a monotonic clock.

| Decision | Required 0.4.0 behavior | Excluded from this adoption |
|---|---|---|
| Automatic continuation | An explicit opt-in resumes one selected interrupted run after acquiring its session writer lock, validating its selected branch, checking remaining limits, and rebuilding its durable checkpoint. A fully committed final assistant response closes the run even if its terminal journal entry was interrupted. | Scanning and resuming every session; reviving cancelled, expired, or failed runs; inheriting an old approval; replaying an external effect with an unknown outcome. |
| Typed task documents | Store small, complete, versioned plan, todo, and goal snapshots in Pi `custom` entries. Each update names the expected previous revision, and a pure branch projection owns the current state. Persist the exact chosen revision as a model-visible message before using it in a request. | New top-level session entry kinds; executable document content; a general patch language; plugin-defined task schedulers. |
| Background compaction | One opt-in session-owned task summarizes a closed prefix. At a later turn boundary, the owner commits a normal Pi `compaction` entry only if the snapshot's ancestry, projected input, retained boundary, and context revision still match. | Mid-stream context replacement; rebasing a stale summary by guesswork; cross-process reattachment; removing synchronous overflow recovery. |

Automatic continuation and effect replay are separate decisions. A synced assistant call proves intent, not dispatch. New journaled runs sync a dispatch record before a tool starts; the current conservative implementation also refuses an incomplete tool exchange without that record. It never replays the pending calls during recovery. A dispatch without a durable result is uncertain. Shell, MCP, plugins, and other tools with external effects stop for reconciliation in that state. A `safe` classification permits rereading only under current policy; an idempotence claim needs a target-enforced key or checked precondition. The runtime promises no automatic replay of uncertain effects, not exactly-once external execution. Old sessions without a dispatch journal cannot prove that a call never started. A recovery notice that informs the model is committed before the resumed request.

Document snapshots carry a document id, kind, revision, previous revision entry id, content, and state. Separate evidence entries name the exact document revision and persisted check result. Model claims and verified state remain separate. Evidence names the checked artifact versions and becomes stale when they change; a successful check over yesterday's files cannot close today's goal. A fork inherits immutable document history at its branch point and creates new execution identities, with no active lease or approval inherited. Branches update their own projections. Ordinary session appends keep Pi’s delayed file creation before the first conversation. Durable journal and document writes use `SessionManager::append_durable_group`, which creates and syncs the Pi file before acknowledging a custom-only group; every written prefix must recover deterministically.

A background summary holds no authority to mutate the session. Its candidate records the source branch and compaction revision, exact input fingerprint, model/settings, and retained boundary. Transcript growth can preserve a candidate only if the summarized prefix remains valid; navigation, context edits, or another compaction can invalidate it. The owner rejects stale candidates and publishes only after the compaction append succeeds. Shutdown, branch switching, or manual compaction cancels and awaits the candidate. Reserve enough allowance for useful foreground work, including both requests a split-turn summary may require. Crashing before commit preserves the original context; crashing after commit rebuilds from the one recorded compaction.

Adoption gates are concrete: kill after each admission, debit, dispatch, result, and terminal-record boundary; prove an external counter is never incremented again for an uncertain effect; race two writer contenders; deny resumed work under current D24 policy; reopen every partial group; compare replayed requests with the committed inputs; reject stale document revisions and evidence; grow the transcript during summarization and invalidate a candidate through navigation and context edits; cancel on each side of the commit; and verify no late task or view update after shutdown. Paired evals must report verified success, unsuccessful clean exits, repeated work, recovery requests, wasted speculative summaries, verification overhead, total tokens, cache reads, and latency. A feature remains opt-in until those records justify a default change.

## Post-0.4.0 candidates

Each of these changes what the model sees, what a released reader must understand, or a public protocol. None is a 0.4.0 requirement. Each needs an owner decision, a regression test, and, when model-visible, a paired eval record.

| Candidate | Benefit | Constraint |
|---|---|---|
| Automatically rerun `safe` tools after a crash | Fewer wasted model round trips after recovery | Changes the model surface; eval against Pi's synthetic `No result provided` result |
| Idempotent submissions keyed by a client request id | Headless and retained transport clients' retries after a crash cannot double-submit | Desktop is deferred beyond 0.4.0 ([D9](scope-00/support.md#decision-register)); a Desktop client needs a coordinated protocol change in a later release |
| Durable background jobs and schedules | Background work survives restarts | Process and sandbox ownership after restart; scope 04 proofs for adopting or killing orphans |
| Hook memos and plugin-defined task types | Native plugins get crash-safe decisions and long-running work | Part of the D6 plugin API design; needs a named consumer |

## Non-goals

- No SQLite, Pi Durable JSONL, or other new storage backend. Pi's session files, with the writer exclusion scope 03 adds, remain the only storage.
- No general scheduler that bypasses the agent owner. Concurrency stays bounded work that returns results to the owner, and only the owner commits.
- No multi-writer or multi-process execution of one session; the writer lock excludes a second writer.
- No unrelated changes to tool names, schemas, results, or recovery messages. D33 governs the baseline; D37 permits the documented opt-in task documents and continuation policy.

## Crash-recovery matrix

Add these cases to [verification](verification.md#acceptance-matrix) as each scope begins. The target acceptance procedure kills the process at the named point, restarts against the same home, and checks the session file, artifacts, process table, and rebuilt request. ## Dev Note

`AgentSession::prompt_recoverable`, `inspect_run`, and `resume_run` implement explicit selected-run recovery; print mode exposes `--recoverable` and `--resume-run <id> --session <path>`. The journal restores spent logical admissions, conservatively refuses incomplete tool exchanges, and reconciles a durable final assistant response without another provider request. Interrupted timed runs cannot continue across processes. Versioned task documents and artifact evidence are implemented in the SDK; the opt-in `task_document` tool can revise documents but cannot manufacture verification evidence. The product has no automatic verifier or verified-goal presentation. SDK evidence binds the declared revision, command, and artifact versions under a trusted host’s execution context. Equal before-and-after hashes do not prove continuous file stability, and imported evidence metadata is unauthenticated; the paired document record measures schema overhead, not verification utility. Background compaction owns one candidate and commits only a still-valid snapshot. These implementations require the paired records and platform checks before release; passing deterministic lifecycle tests alone does not establish a cost or task-success improvement.

This page owns the durable-execution direction and its Pi Durable provenance. The [Pi reference](pi-reference.md) owns the other inspected Pi revisions, and the [support register](scope-00/support.md#decision-register) owns product decisions; any candidate above that is adopted moves into that register first.

**Harness experiments under qualification after the 2026-10-18 audit.** Keep one Pi-style executor and qualify its lifecycle fixes before changing its continuation policy. A run ending says only that execution stopped. Native outcomes distinguish a finished turn, cancellation, exhausted budget, and failure; verified task completion additionally requires evidence for the final artifact versions. The shared run control carries an absolute monotonic deadline and a request allowance through retries, compaction, tools, and completion-notice turns. Exhaustion stops admission and cancels work, then awaits cleanup; the deadline never authorizes abandoning an owned process. Separate cleanup-duration telemetry is not implemented.

| Experiment | Candidate and control | Acceptance evidence |
|---|---|---|
| Selective verification | Compare the existing executor with an optional final or milestone check over the same artifact hashes. A verifier inspects an isolated copy and may write its test outputs there. A changed artifact invalidates earlier evidence. Do not add a manager and auditor to every turn. | Independent fixture checks, false completion count, stale evidence rejected, repair requests, verification tokens, and total latency. Charge verification against the same task budget. |
| Context reduction | Compare current compaction with masking older tool observations, then a masking-plus-compaction arm. Preserve the session log, tool-call/result pairing, recent errors, and the exact deterministic projection needed to reconstruct each request. | Paired long-session success, repeated reads, retained facts, cache reads, summary requests, tokens, and latency. Tune thresholds on separate tasks; do not copy a paper's window size. |
| Bounded tool parallelism | Compare existing unbounded read batches with caps of one and four trusted read tools. Batches containing a mutation remain serialized. Treat shell, unknown tools, and state-changing tools as barriers. Preserve source-order result persistence and approval and cancellation ownership. | Controlled overlap and barrier tests, active-task bound, equal final files and permissions, cancelled work drained, plus paired task success and latency. Keep sequential tasks in the comparison. |

These are hypotheses. [LongHorizon-Harness](https://arxiv.org/html/2608.01964v1) supports independently checking the environment while retaining an executor's native loop, but its cost varies by benchmark and its GUI comparison also changes available capabilities; it does not isolate the value of each role. [The Complexity Trap](https://arxiv.org/html/2508.21433v3) motivates a masking control, with model-dependent quality losses and cache tradeoffs that prevent treating masking as a universal improvement. [Towards a Science of Scaling Agent Systems](https://arxiv.org/html/2512.08296v3) motivates testing parallelizable and sequential workloads separately; its multi-agent results do not establish that any particular Bake scheduler improves task success.

The owner adopted the three [opt-in features](#opt-in-features-for-040) on 2026-10-18 under D37; release qualification remains open. Measurement must use native-versus-native arms, independent artifact checks, three trials across the standard and extended model sets, and all evaluator failures retained. Lifecycle measurements also need deterministic full-pipe, provider-stall, cancellation, and crash fixtures, since a live model's success rate cannot prove those properties.

The audit retains one executor with mandatory durable commits, isolated observers, owned cleanup, and shared run limits. `prompt_recoverable_with_job_wait` includes job notices within the selected journal before its terminal record; neither a notice nor a resumed caller can replace the saved allowance. Interrupted job waits refuse continuation when their original deadline cannot be established. The ordinary print path also retains one control through its notice turns and checks persistence again after shutdown.

The adopted features remain opt-in. Enabling the task_document schema increased paired tokens by roughly 10–21%, and no evaluated model called `task_document`; verification utility remains unmeasured. Recovery's uninterrupted live runs prove journal overhead and task behavior, while the separate process fixtures prove conservative restart decisions. Masking can eliminate summaries and still increase tokens by losing cache reuse. Successful read trials preserve the required facts but do not establish an I/O speedup. Background compaction's valid-commit and cancellation rules are tested; canceled provider usage remains unknown when no final counters arrive. These results support retaining the controls and their explicit activation, with no default promotion or universal efficiency claim.
