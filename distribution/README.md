# Bake direct download releases

The `bake-downloads` Railway service in project `28ff3000-7240-4c57-81d1-7bd05445c1ee` serves a release manifest and installers at `https://bake.justar.dev`, and redirects each versioned platform archive to the asset of the same name on that version's GitHub release. The service exists, but a release is available only after its archives are built, checked, and deployed. Bake still runs on Node; Bun builds the workspace and installs the production dependency graph into each archive.

0.3 bug and security maintenance ends when 0.4.0 ships. That release ships only Rust Bake and retires supported legacy `dsh`, profile, and package aliases ([D10 and D13](../docs/roadmap/rust-0.4/scope-00/support.md#decision-register)). Scope 16 must leave the existing updater on the final TypeScript release, publish Rust through a separate route, and reject later 0.3 publication. The [native preview archive](#native-preview-archive) is packed locally, and the [native release](#native-release) route signs, stages, verifies, and serves it with the channel safeguards those decisions require; the [native installers](#native-installers) install from it and the Rust updater updates and rolls back through it. Nothing has been published on that route and its signing key is still a placeholder, so no release qualifies yet. The other commands below describe the current TypeScript distribution, which 0.3 versions are released from `release/0.3` with, including `release:verify-local`'s install step: that check drives the frozen 0.3 installers kept in [`scripts/release/fixtures/legacy-0.3/`](../scripts/release/fixtures/legacy-0.3/README.md), because the host's own `install.sh` and `install.ps1` are now the native ones.

## Build and check one platform locally

Use a clean checkout with stable Bun 1.4.2 (pinned in `package.json`), Node 24 or newer, and the host native build prerequisites. Run `bun install --frozen-lockfile`, `bun run build`, then:

```sh
bun run release:pack
BAKE_RELEASE_SIGNING_KEY_FILE=~/.config/bake/release-signing-key.pem bun run release:assemble
bun run release:verify-local
```

`release:pack` creates `.artifacts/bake-release/<Bake version>/bake-v<Bake version>-<platform>.tar.gz`. It requires the root and CLI versions to match, copies the declared package payload roots, licenses, changelog, and built files, then runs a frozen production Bun install in a temporary workspace and runs the staged CLI's `--self-check`, the launch check `bake update` runs before switching to a release: it composes the shipped `tui` and `headless` profiles and loads every plugin they name, the agent presets' plugins, and the terminal's runner modules. Outside Windows that install uses the linker the root `bunfig.toml` sets, so the archive's `node_modules` has the hoisted layout development and CI resolve through. Windows keeps Bun's isolated layout, where a package resolves only the dependencies it declares, so a runtime import listed only under `devDependencies` fails there alone. Then the stage's group and other write permission is cleared before the system `tar` records it. Installers and `bake update` only unpack the archive; nothing installs dependencies on a user's machine. `release:assemble` hashes every archive for the current Bake version, writes `distribution/host/public/latest.json` plus the versioned archives, and signs the manifest's exact bytes into `latest.json.sig`. The local check verifies that signature, rejects an archive with any group- or world-writable entry other than a symlink, serves those exact files over HTTP, runs the frozen 0.3 platform installer from [`scripts/release/fixtures/legacy-0.3/`](../scripts/release/fixtures/legacy-0.3/README.md) into temporary directories, checks that the installed `node_modules` has the workspace's layout, and boots the installed command. Windows archives are exempt from the permission check: `tar.exe` records every entry there as writable by all, and Windows ignores those bits when it unpacks. It then publishes a release one patch newer, built from the installed files and signed by a key of its own, and updates to it with `bake update`: it checks `bake update --check`, a refused update when the newer manifest's key is not trusted, the update itself, `bake --version`, where `current` points, and that the replaced release is still on disk. Last, `bake update --rollback` returns to the staged release, checked by `bake --version` and where `current` points, and a second rollback, with nothing older installed, fails without moving `current`. These generated paths are ignored by Git.

### The release signing key

Installers and `bake update` trust a manifest only when the Ed25519 key in `distribution/host/release-key.pub` signed it; the same public key is written into both installers and `RELEASE_PUBLIC_KEYS` in `packages/boot/updater/src/keys.ts`, and a release test holds every copy equal. The private half never enters the repository: keep it as a PKCS#8 PEM file readable only by the release owner, and name it with `BAKE_RELEASE_SIGNING_KEY_FILE`. `release:assemble` refuses to run without it, and refuses a key whose public half differs from `release-key.pub`. A check without the key, such as CI, runs `bun run release:assemble --ephemeral-key`: it signs with a throwaway key and leaves the public half as `ephemeral-release-key.pub` beside the archives, where `release:verify-local` passes it to the clients through `BAKE_RELEASE_PUBLIC_KEY`. The download service's image build sets no such variable, so a manifest signed with a throwaway key never deploys. To rotate the key, add the new public key to `RELEASE_PUBLIC_KEYS` in a release signed by the old one, then sign with the new one.

Build each target on its own host: `darwin-arm64`, `darwin-x64`, `linux-arm64`, `linux-x64`, and `win32-x64`. The [live manifest](https://bake.justar.dev/latest.json) names the platforms currently available. Verified platforms may be published independently. Collect the archives to publish in the same `.artifacts/bake-release/<Bake version>/` directory before assembling. When adding a target to an existing version, include every already published archive to keep it available; download those archives from the current manifest and verify their SHA-256 hashes before assembling. A single host build proves only its own target; the Windows installer and native modules need a Windows run. For a complete release, run `bun run release:assemble --complete` and `node distribution/host/verify-manifest.mjs --complete`. Every release version must be new: an installed release is named by its version and archive hash, and `bake update` offers only a version newer than the running one.

## Native dependency licenses

The Rust agent's third-party license bundle is generated separately from the TypeScript archives. The [native preview archive](#native-preview-archive) carries its platform's text; nothing publishes it yet. It needs the Rust toolchain pinned in `rust/rust-toolchain.toml` and cargo-about 0.9.2, installed with `cargo install cargo-about --version =0.9.2 --locked --features cli` (the `cli` feature carries the binary) or named with `BAKE_CARGO_ABOUT`; any other version is refused.

```sh
bun run gen-native-licenses     # cargo fetch --locked, then write .artifacts/native/licenses
bun run verify-native-licenses  # regenerate offline and compare; leave the bundle unchanged
```

Both commands take `--out <dir>`, resolved through any links: inside the repository it must be under `.artifacts/native/`, and `distribution/`, `.artifacts/bake-release/`, and a link to a missing path are refused. `--write` replaces only an empty directory or an earlier bundle with nothing else in it. It stages the new bundle beside the output and removes the earlier one only after the new one is in place. If installation fails, it restores the earlier bundle; if restoration also fails, the error names the directory where the earlier files are kept.

Collection uses cargo-about's output-file option so PowerShell does not alter or reject captured license text. The private temporary output is removed after either success or failure; checking never changes the bundle directory.

The output is `inventory.json` and `<platform>/THIRD-PARTY-LICENSES.txt` for each of the five platforms a native manifest can name, so the macOS and Windows texts stay generated for 0.4.x although 0.4.0 packs Linux alone. Each file lists the locked crates with their declared licenses and roles, reproduces their license texts with source paths, and includes Bake's crate NOTICE files, the `LICENSE-*` files of third-party artifacts a Bake crate embeds (each in an immediate subdirectory of the crate, such as `bake-codemode`'s `engine/` for its vendored QuickJS-NG binary and the wasi-libc, musl, and cloudlibc code inside it), and third-party NOTICE, COPYRIGHT, and COPYING files. Dev-dependencies are excluded. Output is byte-identical for the same inputs and carries no machine paths.

The generator selects `runtime` crates with `cargo tree -p bake-cli --target <triple> -e normal,no-proc-macro`. Its `build` list includes the build-dependency and proc-macro subtrees of those crates from `cargo tree --target all -e normal,build --no-dedupe`. Cargo evaluates build-host `cfg()` for the running host, so a per-target tree printed on Linux can omit a Windows runner's build dependencies. The `build` list therefore includes all build hosts and can name crates a given runner does not build.

[`rust/about.toml`](../rust/about.toml) is the license policy: cargo-about chooses each crate's license from its accepted list, in order, and fails on a crate none satisfies. [`scripts/release/native-licenses.ts`](../scripts/release/native-licenses.ts) verifies that cargo-about covers every selected crate and that each text appears verbatim in that crate's source package. Locked crates reported only by cargo-about's broader target selection are excluded and listed in the inventory. A clarification must name a selected crate, preserve its declared license, and match its source-file hashes for every selected version. A dependency change needs a regenerated bundle; a new license or an unrecognized license file needs a reviewed edit to `about.toml`. A crate published without the license file its repository keeps, as Wasmtime's internal crates are, takes a reviewed copy vendored under `rust/licenses/` and listed in `rust/licenses/upstream.toml`. The entry pins the file's SHA-256, the repository commit and path with its raw URL, and each inheriting crate's `name@version`, `Cargo.lock` checksum, and `.cargo_vcs_info.json` path. Generation never downloads it, uses it only where cargo-about found no text, and fails when any pin differs or no selected crate needs the entry. The generator trusts cargo-about's license detection.

## Native preview archive

`bun run release:pack:rust` builds `bake` for this host with the toolchain `rust/rust-toolchain.toml` pins (`cargo build --locked --release -p bake-cli`, run from `rust/`) and writes `.artifacts/bake-native-release/<Cargo version>/bake-v<Cargo version>-<platform>.tar.gz`, for example `bake-v0.4.0-dev-linux-x64.tar.gz`. The version is `bake-cli`'s Cargo version from `cargo metadata`, not `package.json`, so the 0.4 development version packs without touching the 0.3 manifests. The platform is the host's, and Bake 0.4.0 packs only `linux-x64` and `linux-arm64` ([D47](../docs/roadmap/rust-0.4/scope-00/support.md#decision-register)): on a `darwin-arm64`, `darwin-x64`, or `win32-x64` host the command stops before it builds, saying those archives arrive in Bake 0.4.x. Any other host, or a request for another platform, is refused, because an archive is checked by running its binary. `--profile dev` packs the debug build instead, and `--out <dir>` writes elsewhere. The output directory is checked before the build and again once created, with its existing ancestors resolved through symbolic links and junctions: it must be outside the repository or under `.artifacts/bake-native-release/`, and never inside `.artifacts/bake-release/` or `distribution/host/public/`, so a link cannot route the native archive into the TypeScript release; a link to a missing path is refused. Bun runs only this build tool; the archive needs neither Node nor Bun.

The archive holds `bin/bake` (`bake.exe` on Windows, mode 0755), `LICENSE`, `THIRD_PARTY_NOTICES.md`, `notices/<crate>/NOTICE` for each workspace crate `bake-cli` links, which keep Pi's MIT notice for the ported crates, and the [dependency license bundle](#native-dependency-licenses)'s `licenses/inventory.json` and `licenses/<platform>/THIRD-PARTY-LICENSES.txt` for this platform alone, in the bundle's own layout so the inventory's file paths resolve; directories are 0755 and other files 0644. It holds no Node, Bun, `node_modules`, TypeScript product code, launcher, or manifest, and nothing creates a `bake` or `dsh` command. Every payload source must be a regular, non-empty file; a symbolic link is refused rather than followed. The staged binary runs `--version` and [`--self-check`](../rust/README.md) in a private empty home with an empty PATH, which must stay empty, for at most 30 seconds and 1 MiB of output per stream; past either, the binary is killed and both output reads are cancelled and awaited, along with the binary's exit, before its temporary directory is removed. Only that binary is killed: a process it started and left running is not, though it cannot hold the check open. `bake` starts none for these commands. The checks require the version to equal the Cargo version, the self-check's platform to equal the host's, and its documentation hashes to equal the `rust/crates/bake-cli/docs/*.md` sources, so a stale or foreign binary is refused. On macOS, archiving omits AppleDouble files and source ACLs, extended attributes, and file flags. The system `tar` writes an archive in the private staging directory using ASCII relative paths; it is read back to require exactly the staged files and directories, with no links, duplicates, or group- or other-writable modes and an executable binary (modes are not checked on Windows, whose `tar.exe` invents them), unpacked into another private directory, compared byte for byte, and its binary checked again. Only then is it copied to an exclusive partial file beside the destination and renamed into place, so any failure leaves an earlier archive as it was. The command prints the archive listing, the self-check record, and the canonical archive path.

The license files are generated for each run, never read from an earlier `gen-native-licenses` output: before building, the command runs `cargo fetch --locked`, the only step that may use the network, then the generator's own collection and checks, offline, so it needs cargo-about 0.9.2 as that section describes. A missing or other cargo-about, or a crate whose license the generator cannot cover, fails the command before anything is built and leaves an earlier archive as it was. The packager adds no license policy and reads no dependency graph; it checks that the bundle describes this build: a `bake-native-licenses/1` inventory generated by cargo-about 0.9.2, every input file it records, including `rust/Cargo.lock` and `rust/about.toml`, unchanged in this checkout, each platform text present and matching its inventory hash with nothing unlisted, this platform's text headed with its own platform and triple, `bake-cli` at the packed version, and the Bake crate NOTICE files it reproduces for this platform the same set, with the same bytes, as those archived under `notices/`. Any difference fails before the binary runs. After the archive is unpacked, both license files must equal the generated bytes.

This is the package layout alone, not a release: the archive is hashed into a manifest and signed by the [native release](#native-release) route, and nothing yet uploads, installs, updates, or rolls back a native archive. Each platform's archive must be built and checked on that platform. The native preflight group runs `bun run test:rust:package` on each host it runs on: on Linux it packs and runs the debug build, which CI does on x64 and arm64 Linux, and on macOS and Windows it shows the pack refusing before it builds. That check compares the archived license files with a separate `gen-native-licenses` run byte for byte and fails, rather than skips, without cargo-about 0.9.2. CI's native job builds that exact version with `cargo install --locked`, caches it per runner OS and architecture, and names it with `BAKE_CARGO_ABOUT`; a Mac running `bun run preflight:mac` needs it on PATH or named in the command. Owner-group and reproducible-timestamp normalization are not applied.

## Native release

The Rust agent is published on its own route of the same host, separate from the frozen TypeScript one ([D45](../docs/roadmap/rust-0.4/scope-00/support.md#decision-register)). The user-facing command the native install provides is `bake`.

| Route | What it serves |
|---|---|
| `/native/stable.json` | the native release manifest |
| `/native/stable.json.sig` | base64 Ed25519 signature over that file's exact bytes |
| `/native/releases/<version>/<file>` | the native archives |

`/latest.json` and `/releases/<version>/<file>` stay the TypeScript route, frozen on the final 0.3 release so existing 0.3 updaters keep reading it; a native archive never appears there, and a 0.3 updater can neither verify nor parse a native manifest.

```json
{"schema":"bake-native-release/1","channel":"stable","version":"0.4.0","published":"2026-10-20T00:00:00Z","artifacts":{"linux-x64":{"file":"bake-v0.4.0-linux-x64.tar.gz","sha256":"<64 lowercase hex>","size":123}}}
```

The manifest is UTF-8 JSON with exactly those members: `version` is canonical SemVer, `MAJOR.MINOR.PATCH` with an optional prerelease and no build metadata, where no number or numeric prerelease identifier has a leading zero and no identifier is empty; every reader orders versions by SemVer precedence, which over canonical versions is total. `published` is UTC with second precision, and `artifacts` names a non-empty subset of `darwin-arm64`, `darwin-x64`, `linux-arm64`, `linux-x64`, and `win32-x64`. The grammar keeps all five so a 0.4.x release can add a platform without a new schema, but Bake 0.4.0 publishes `linux-arm64` and `linux-x64` alone: the assembler and the host gate refuse a manifest naming any other. Each artifact carries only `file`, which must be the [packager's](#native-preview-archive) archive name for that version and platform, a lowercase hex `sha256`, and a positive `size`. Any unknown member, in the manifest or an artifact, is refused. Its canonical bytes are those members in that order, the artifacts in platform order, on one line with a trailing newline, and the signature covers those exact bytes, so a reformatted manifest no longer verifies. [`scripts/release/native-manifest.ts`](../scripts/release/native-manifest.ts) writes and parses them, and `bake` reads the same rules.

### The native signing key

`distribution/host/native-release-key.pub` holds the native public key, base64 DER SubjectPublicKeyInfo as `release-key.pub` does, and is a different key: the 0.3 updater's trusted keys never include it, so no 0.3 install can be moved by a native manifest. It is a **placeholder** today, generated in a throwaway process that discarded the private half, and `distribution/host/native-release-key.placeholder` marks it. While that marker exists, `bun run release:preflight` fails, `release:assemble:rust` refuses to sign with the committed key, and the host's native gate refuses a staged native manifest, so nothing can be published under a key nobody holds. Tests sign with ephemeral keys only.

The release owner replaces it once, before 0.4.0. Generate the key where the private half will stay, keep it out of the repository, and print the public half:

```sh
umask 077 && node -e "const { generateKeyPairSync } = require('node:crypto'); const key = generateKeyPairSync('ed25519'); require('node:fs').writeFileSync(process.argv[1], key.privateKey.export({ type: 'pkcs8', format: 'pem' })); console.log(key.publicKey.export({ type: 'spki', format: 'der' }).toString('base64'))" ~/.config/bake/native-release-signing-key.pem
```

Write that printed line, with a trailing newline, into `distribution/host/native-release-key.pub`, delete `native-release-key.placeholder`, and commit both; `bake` embeds the same file. Name the private file with `BAKE_NATIVE_RELEASE_SIGNING_KEY_FILE` or `--key-file` when assembling. Rotation needs the new key trusted by a native release signed with the old one, as the 0.3 key's section describes.

### Assembling and verifying a native release

Pack each platform on its own host, collect every archive of the version in `.artifacts/bake-native-release/<version>/`, then sign them into the service payload and check the result:

```sh
bun run release:pack:rust      # on linux-x64 and on linux-arm64
BAKE_NATIVE_RELEASE_SIGNING_KEY_FILE=~/.config/bake/native-release-signing-key.pem \
  bun run release:assemble:rust 0.4.0
node distribution/host/verify-native-manifest.mjs   # once the key is no longer a placeholder
```

`release:assemble:rust <version>` hashes each archive, copies it to `distribution/host/public/native/releases/<version>/`, and writes the manifest and its signature to `public/native/`. It refuses an archive whose name is not that version's archive for a release platform, a `darwin-*` or `win32-x64` archive, which 0.4.0 does not publish, an archive that is not a native archive — one lacking the native executable with `licenses/inventory.json` and `notices/`, or holding a TypeScript release's Node launcher, `node_modules`, or `apps/cli/lib/bin.js` — an empty set of archives, and a link or escaping path inside an archive. `--complete` also requires both `linux-x64` and `linux-arm64` archives. `--ephemeral-key` signs a local check with a throwaway key and leaves its public half beside the archives as `ephemeral-native-release-key.pub`; `--offline` publishes without reading the live channel. The signing key is resolved, and the channel checked, before anything is staged. These generated paths are ignored by Git.

`verify-native-manifest.mjs` is the native gate the service's image build runs, mirroring `verify-manifest.mjs`: it verifies the signature against the committed native key alone, applies every member rule above, refuses a manifest naming a macOS or Windows archive whatever its flags, and checks each archive's size and SHA-256. `--complete` requires exactly `linux-arm64` and `linux-x64`, `--allow-missing-archives` accepts an archive the image does not hold, because the server redirects those to the version's GitHub release, and `--required` refuses a payload with no native manifest, which otherwise reports that none is published. A local check names a throwaway key with `BAKE_NATIVE_RELEASE_PUBLIC_KEY`, which the image build never sets, as the 0.3 gate's `BAKE_RELEASE_PUBLIC_KEY` does. While `native-release-key.placeholder` exists the gate refuses any staged native manifest before it reads a key, so an ephemeral round trip can only run it in a copy of `distribution/host/` without that marker, as [`native-manifest.test.ts`](../scripts/release/native-manifest.test.ts) does; the command below reads the gate as written once the owner has replaced the key.

### The glibc floor

`bun scripts/release/glibc-floor.ts <binary> [--floor GLIBC_2.34]` reports the oldest glibc a built Linux `bake` starts on and fails when that is above `--floor`; [`glibc-floor.ts`](../scripts/release/glibc-floor.ts) names the default, glibc 2.34, the floor the release owner chose ([D50](../docs/roadmap/rust-0.4/scope-00/support.md#decision-register)), which RHEL 9 and its rebuilds, Amazon Linux 2023, Ubuntu 22.04, and Debian 12 meet. It reads the binary's version needs with `readelf --dynamic --version-info` from binutils, run in the C locale because readelf translates its headings. The floor is the highest `GLIBC_` need that is not weak: Rust's standard library binds some newer functions weakly and falls back where the host lacks them, so those are reported beside the floor without raising it. It fails closed: output without a dynamic section report, or a binary whose dynamic section lists a shared library while no glibc version need can be read, is an error, not a pass. A binary whose dynamic section lists no shared library, a static or static-pie one, is reported as statically linked and passes. CI's native job runs it on Linux against the debug build its preflight leaves, whose needs match the release build's.

`server.mjs` serves the three native routes with the 0.3 route's behavior: the manifest and signature uncached, the archives immutable for a year, and an archive the image does not hold redirected to `<redirect>/v<version>/<file>`. Nothing else under `/native/` is served. The two channels are counted apart in the service's daily count of active installs. The native channel is counted by its route rather than by a client's user agent, so the native updater needs no user-agent contract: every `GET /native/stable.json` is reported, as product `bake` with channel `native`, including an install that is reading the manifest to install itself. The 0.3 report is unchanged, product `bake` with no channel, and still counts only Node's own client. A day's count holds one entry per address and channel, through unrelated daily hashes, so the same address on both channels is counted once on each.

### Channel safeguards

Publication cannot route a native archive to a 0.3 updater or move either channel backward.

- The 0.3 `release:assemble` refuses a native archive, by its name and by its layout, and refuses to write `latest.json` at all once a native release of 0.4.0 or later is staged in the public directory, because 0.3 publication ends when 0.4.0 ships (D13). A native manifest it cannot read refuses it too, rather than being ignored.
- `release:assemble:rust` refuses a version that is not strictly newer than the published native release, checked against both the staged `public/native/stable.json` and, unless `--offline`, `https://bake.justar.dev/native/stable.json`, where a 404 means none is published yet. A live channel that answers anything else refuses the run. There is no republication of a native version.
- `release:assemble:rust` writes `public/native/` alone: never `latest.json`, its signature, or `releases/`.

[`scripts/release/native-archive.ts`](../scripts/release/native-archive.ts) owns the layout rules both assemblers apply, and [`native-channel.ts`](../scripts/release/native-channel.ts) the retirement and key-readiness checks. Their tests cover each refusal, a round trip from archives through assembly, the host gate, and the server, and hold the frozen 0.3 updater's own manifest parser and signature check against a native manifest, which it refuses.

## Native installers

`distribution/host/install.sh` and `install.ps1` install the Rust agent from the native release route, in place of the 0.3 installers, which stay on `release/0.3` ([D45](../docs/roadmap/rust-0.4/scope-00/support.md#decision-register)). Nothing about them runs Node or Bun.

```sh
curl -fsSL https://bake.justar.dev/install.sh | sh
```

```powershell
irm https://bake.justar.dev/install.ps1 | iex
```

Each installer reads `<host>/native/stable.json` and `<host>/native/stable.json.sig`, verifies the signature over the manifest's exact bytes against the key it carries, then checks the manifest against the `bake-native-release/1` grammar: exactly `schema`, `channel`, `version`, `published`, and `artifacts`, a canonical SemVer version, artifact keys from the five manifest platforms with no repeats, a `file` equal to `bake-v<version>-<target>.tar.gz`, a 64 lowercase hex `sha256`, and a positive safe-integer `size`. Any other document, including one with an unknown member, is refused. The archive must then match that size and hash, and every member must be a plain file or directory with a relative path and no `..` component; a link or special member is refused before anything is unpacked, as is an archive whose members together unpack to more than 512 MiB, the bound `bake-update` applies too. `BAKE_DOWNLOAD_URL` names another host, for a local check.

Bake 0.4.0 publishes Linux releases alone, so both shipped installers refuse macOS and Windows before they download anything or create the install root: `install.sh` on a `Darwin` host, once it has named the platform, and `install.ps1` at its start, with a `throw` rather than an `exit` so a refused `irm | iex` leaves the user's shell open. Each prints `Bake install: Bake 0.4.0 releases linux-arm64 and linux-x64 only; native <platform> releases arrive in Bake 0.4.x`; `install.sh --uninstall-links` still runs there. The refusal is a marked block in each script, and the tests run the rest of the installer, which the 0.4.x releases for those platforms ship, through a copy without it.

An installer never replaces the running release until the candidate proves itself: the unpacked tree's own `bin/bake` (or `bin/bake`) runs `--self-check` within a deadline and must report the manifest's version and this host's platform. Only then is the tree renamed into place and the pointer moved. A release older than the installed one is refused as a rollback attempt, by the same SemVer precedence `bake-update` applies: numeric identifiers compare by value at any length, alphanumeric ones as ASCII text, a numeric one before an alphanumeric one, and a release after its prereleases, so 0.4.0-rc.10 is newer than 0.4.0-rc.9. Both installers and `bake-update` are tested against one case table, [`fixtures/native-version-order.txt`](../scripts/release/fixtures/native-version-order.txt). The install root holds:

```
<root>/releases/<version>/   one unpacked release each
<root>/current               Unix: relative link to releases/<version>; Windows: current.txt, the version and a CRLF
<root>/previous              the release a rollback returns to (previous.txt on Windows)
<root>/install.lock          the lock every install, update, rollback, and prune holds
<root>/links.json            the commands the installer created or replaced
```

`<root>` is `$BAKE_NATIVE_ROOT`, by default `~/.local/share/bake-native` and `%LOCALAPPDATA%\bake-native`, separate from the 0.3 root, which the native installers only read. Retention keeps `current` and `previous`; a release whose files are held is left for a later prune. A pointer is always replaced by a rename of a temporary link or file, so a reader sees one release or the other; on Unix that needs `mv -T` (GNU) or `mv -h` (BSD), which the installer finds once and refuses to proceed without.

`install.lock` is a directory, created by an atomic `mkdir`, holding one `owner` line of `<pid> <unix seconds> <kind>`, where kind is `install`, `update`, `rollback`, or `prune`. A held lock whose owner process is gone is taken over once; a lock with no owner file counts as held for ten more seconds and is then stale. The Rust updater takes the same lock the same way, so neither side runs while the other does.

The install provides one command, `bake`: `<bin>/bake` links to `<root>/current/bin/bake` on Unix, and `<bin>\bake.cmd` on Windows reads `current.txt` on every run and starts that release's executable, so an update never rewrites the file a running `cmd.exe` is reading. `<bin>` is `$BAKE_BIN_DIR`, by default `~/.local/bin` on Unix and, on Windows, the 0.3 `bin` directory when it exists and is already on the user PATH, so the takeover replaces the command the PATH names, and otherwise `<root>\bin`, which is added to the user PATH.

The installer takes over a Bake-managed 0.3 `bake`, meaning a link into the 0.3 root or a `bake.cmd` with the 0.3 launcher text, and records the old target or a backup of the old file in `links.json` (`bake-native-links/1`). A `bake` no Bake installer made is left alone: the release is installed, the installer exits non-zero naming the file, and `--replace-command` (`BAKE_REPLACE_COMMAND=1` for a piped install) replaces it and keeps a restorable backup. Running the installer again, which is how an install is updated, keeps the command it already made and leaves `links.json` as the first run wrote it, so the 0.3 command it took over stays restorable and no backup accumulates. `--uninstall-links` puts back whatever `links.json` records and removes the commands the installer created, each only while that path still holds the command this installer made; one a user has replaced since is left alone. `dsh`, the 0.3 install, and its data are never written to; a 0.3 `bake update` leaves a taken-over `bake` alone, because its only command-directory step adds a missing `dsh` beside a `bake` that still leads to a 0.3 release ([`legacy-updater-takeover.test.ts`](../scripts/release/legacy-updater-takeover.test.ts)).

Unix needs `curl` or `wget`, `tar`, and `sha256sum` or `shasum`. The manifest signature is Ed25519, and `install.sh` finds a verifier for it before it reads anything: it tries `$BAKE_OPENSSL`, `openssl` on PATH, `/opt/homebrew/opt/openssl@3/bin/openssl`, and `/usr/local/opt/openssl@3/bin/openssl`, in that order, and names one of them only once it has verified RFC 8032's TEST 2 signature over that vector's own message and seen it refused over another; `BAKE_OPENSSL`, when set, is the only openssl tried. macOS ships LibreSSL, whose `openssl(1)` has neither `pkeyutl -rawin` nor Ed25519, so a stock Mac has none that passes and falls back to the Ed25519 verifier `install.sh` embeds, run with `osascript -l JavaScript`: the script assembles R, A, and the manifest and takes their SHA-512 with `shasum -a 512`, and the JavaScript decompresses the points and applies RFC 8032 section 5.1.7's cofactorless check, refusing an unreduced `S`, a non-canonical `R` or key, and any wrong length. Only `osascript` runs that path, and it too is proven on the vector first; with no verifier at all the installer stops, names what it tried, and says to `brew install openssl@3`. The step the install prints names the verifier it used. Windows needs `tar.exe` and verifies the signature with the same algorithm implemented in `install.ps1` itself, because neither Windows PowerShell nor Windows CNG has Ed25519 and no Node runs.

Both installers carry the native release key, `distribution/host/native-release-key.pub`, in one line each, and [`native-install.test.ts`](../scripts/release/native-install.test.ts) holds every copy equal. The tests never steer a published installer: each scenario copies the script and replaces that one line with an ephemeral key, so no environment variable can add a trusted key. `native-install.test.ts` runs the shell installer against a loopback host for a fresh install, an update, a rerun that keeps the 0.3 restore record, the 0.3 takeover and its restoration, a user-owned command, refused manifests and archives, an archive past the unpacking bound, a failed self-check, an openssl that fails its probe, the embedded verifier's own path, and the lock's contended, taken-over, and owner-less cases; it is skipped on Windows, which `install.sh` has no target for. [`native-install-ed25519.test.ts`](../scripts/release/native-install-ed25519.test.ts) runs the JavaScript verifier `install.sh` embeds, extracted from the shipped heredoc, against RFC 8032's vectors, every tampered form, and 50 `node:crypto` signatures with their tampered twins; macOS CI installs once with `BAKE_OPENSSL` naming no openssl, which forces that text through real `osascript`. [`native-install-windows.test.ts`](../scripts/release/native-install-windows.test.ts) runs the shipped PowerShell verifier against RFC 8032 vectors, tampered forms, and 50 signatures from `node:crypto`, then the installer itself, through a file and through `iex`, wherever a `pwsh` is available (`BAKE_TEST_PWSH`, `.preflight/tools/pwsh`, or PATH); on Windows its release fixture is a compiled executable, because Windows starts no script as one.

`bun run test:rust:install` is the rehearsal ([`native-rehearsal.native.ts`](../scripts/release/native-rehearsal.native.ts)): it archives the `bake` this checkout builds in the packager's layout, with `strip -S` removing the debug information a debug build carries past the 512 MiB unpacking bound, publishes it to a loopback host, installs it with the shipped `install.sh`, and runs `--version` and the real `--self-check` through the installed command, then installs a fixture second version so `previous` names the real release. Its archive carries placeholder license files, because the real bundle needs cargo-about, which `release:pack:rust` and `test:rust:package` cover. Release qualification still needs this run on linux-x64 and linux-arm64, an update and rollback driven by the native updater itself, and the D46 plugin consumer against the installed artifact; the Windows installer's run on Windows waits for the 0.4.x Windows release.

## Release with GitHub Actions

The [release workflow](../.github/workflows/release.yml) builds, checks, signs, and publishes every platform from one tag. This page describes a release from `develop` through `main`, which is next used for the Rust release, 0.4.0, once the [roadmap's release qualification](../docs/roadmap/rust-0.4/README.md#release-qualification) passes. 0.3 versions of the frozen TypeScript agent are released from `release/0.3`, whose copy of this guide and of the workflow describes that path.

```sh
# on an up-to-date develop, after the release's last change is pushed
NEXT=0.1.2                           # choose a stable version newer than the current one
bun run release:prepare "$NEXT"       # both manifests, bun.lock, and a CHANGELOG.md section
# write the new section in CHANGELOG.md, then:
bun run release:preflight --offline --tag "v$NEXT"
git add package.json apps/cli/package.json bun.lock CHANGELOG.md
git commit -m "release: $NEXT"
git push origin HEAD:develop
gh pr create --base main --head develop   # CI runs here; fix failures on develop
# once that pull request merges:
git switch main && git pull --ff-only
git tag "v$NEXT"
git push origin "v$NEXT"
```

`main` takes changes only through merge-commit pull requests from `develop`, so the release commit reaches it that way and the tag goes on `main`'s merge commit. If `evals/agent-loop/versions/unreleased/` exists, rename it to `v$NEXT` in the release commit as well. `release:prepare` moves the `[Unreleased]` changelog entry under the new version, or leaves a placeholder the release refuses. It accepts stable versions with canonical numbers, such as `0.1.1`. The pushed tag starts the workflow:

1. **preflight** (`release:preflight`) checks that the tag points to a commit on the default branch, names the workspace version, and has a written changelog section. It compares the version with the signed download manifest, or with GitHub's latest published release when the download service is off. The deployed unsigned `0.1.0` manifest is the sole signing exception for the first transition.
2. **build** runs on one runner per target — `ubuntu-24.04`, `ubuntu-24.04-arm`, `macos-15`, `macos-15-intel`, and `windows-latest` — because the native modules are compiled for the host. Each runner checks it builds its target, packs the archive, installs it with the real installer and updates through it with `bake update` (`release:verify-local`, signed with a throwaway key), and, outside Windows, runs the built-profile terminal scenarios. Every platform reports even when one fails, and publishing needs all five.
3. **publish** runs in the `release` environment, the only place the signing key and deploy token exist. It signs the manifest (`release:assemble --complete`), runs the image's signature gate, and checks that a retry does not change any archive already served under this version. It uploads the archives, manifest, signature, and installers to a GitHub release draft and downloads them again to compare every byte. It publishes the draft and verifies it as a client reads it, because the download service redirects its archives there. It then deploys the download service without the archives, which together exceed Railway's upload limit, and waits for the manifest and every archive to become available through it. A rerun keeps an already published GitHub release's assets and only proves they match this build.

Run the workflow by hand from the Actions tab for a dry run: it builds and checks all five platforms and publishes nothing, even when started from a tag. If a tagged run fails before publication, rerun it; a matching version already deployed by that run is allowed, but different archive bytes are refused. If it fails after the GitHub release is public, check the hosts with `bun run release:verify-live <version> --complete` and inspect the failed step before starting a new version.

Before the first tagged release, create the `release` environment under the repository's settings, limit it to tags matching `v*`, and, if releases should wait for a person, add a required reviewer. Give it the signing key and, when deploying the download service, a Railway token:

| Secret | Value |
|---|---|
| `BAKE_RELEASE_SIGNING_KEY` | The whole PEM text of the release signing key |
| `RAILWAY_TOKEN` | A Railway project token for the `production` environment of the download service's project; needed unless `BAKE_DOWNLOAD_SERVICE=off` |

The download service counts active installs for gissx.org's admin when its Railway service has all three of these variables; without them it reports nothing:

| Service variable | What it is |
|---|---|
| `GISSX_ACTIVITY_URL` | `https://gissx.org/api/activity` |
| `GISSX_ACTIVITY_TOKEN` | The bearer token gissx.org's Worker holds as `ACTIVITY_TOKEN` |
| `BAKE_ACTIVITY_SALT` | Any long random string; it salts the daily install hash, and changing it starts the count afresh |

An installed Bake fetches `latest.json` with Node's own client when it checks for updates, at most hourly, so the service reports each such request as one install in use. Installers, browsers, and the release workflow's checks use other clients and are not counted. A native install is counted on its own channel instead, as the [native release](#native-release) section describes. The service sends the install as a daily salted hash of its address, at most once a day, so no address leaves it; reporting runs after the response and never delays or fails it.

The GitHub release is a release host of its own: it carries the signed manifest beside the archives, and the installers and `bake update` accept `BAKE_RELEASE_BASE_URL=https://github.com/Justar96/bake/releases/latest/download`, fetching each archive from its own tag. Its assets download without a login only once the repository is public, and the workflow verifies the published GitHub release as a client reads it. Set the repository variable `BAKE_DOWNLOAD_SERVICE` to `off` to publish to GitHub alone; this mode requires a public repository and checks GitHub's latest release before building. Clients then need that host, either through the variable or by making it the default in `packages/boot/updater/src/keys.ts` and both installers.

## Publish a checked release by hand

After every archive listed in the manifest has passed its native local check and is published on the version's GitHub release, run `node distribution/host/verify-manifest.mjs` and deploy the download service from the repository root:

```sh
host="$(mktemp -d)/bake-downloads"
cp -R distribution/host "$host" && rm -rf "$host/public/releases"
railway up "$host" --path-as-root --no-gitignore \
  --project 28ff3000-7240-4c57-81d1-7bd05445c1ee \
  --environment production --service bake-downloads \
  --detach --json -m "Bake CLI direct download release"
```

The `--no-gitignore` flag includes the generated manifest and signature, and the copy leaves out the archives, which the service redirects to `https://github.com/Justar96/bake/releases/download/v<version>/`. The Docker build (`verify-manifest.mjs --allow-missing-archives`) rejects an unsigned manifest or one the committed key did not sign, empty manifests, unsupported targets, invalid names, empty archives, and size or SHA-256 mismatches for any archive it does hold. Use `--complete` for the optional five-platform gate. Record the deployment ID, wait for that deployment to reach `SUCCESS`, then check `/health`, `/latest.json`, `/latest.json.sig`, both installer routes, and each newly published platform archive through the public domain. An upload response alone does not qualify the release. The manifest lists the platforms currently available; the installers fail clearly on an unavailable platform.

`https://bake.justar.dev/install.sh` and `install.ps1` are the [native installers](#native-installers); the TypeScript installers this section's flow needs live on `release/0.3`, with its copy of this guide. The service serves release bytes only and stores no API keys.

Interactive installs and `bake update` open with a `BAKE` heading, then print each step once it finishes, with a check, what was done, and a dim note ending in how long it took (`✓  Downloaded          18.4 MB · 2.1s`), and close with what was installed and the command to run. Only the step still running is redrawn, on one live row: an orbit of four Braille dots circling a square, the step, and a meter. A step whose length is known, the download, fills the meter from orange to amber with a glint sweeping across it, beside its percentage and bytes; a step without one runs a comet back and forth along the track instead of a guessed percentage. A failed step is marked `✗` before the installer's diagnostics. The terminal's `/update` draws the same live row above the composer. A UTF-8 terminal, or Windows Terminal, draws Braille and box glyphs; any other, and a CJK character locale, whose terminals often draw box glyphs two cells wide, get ASCII (`| Downloading  =====>----`). Colour is 24-bit where `COLORTERM` or Windows Terminal says the terminal draws it, and the 256-colour cube otherwise. The rows live in `apps/tui/packages/ui/src/install-progress.ts`, so all three draw the same install. Redirected output, CI, and `TERM=dumb` stay plain. Set `BAKE_NO_ANIMATION=1` to disable motion or `NO_COLOR=1` to omit color. This describes `bake update` and the terminal's `/update` on the frozen TypeScript agent; the native installers print one plain line a step, because they run no Node.

## Updating an install

`bake update`, or `/update` inside the terminal, replaces an install the installers made with the newest signed release, showing download progress as it goes, and `bake update --check` only reports, exiting 0 when up to date, 10 when a newer release is available, and 1 on failure. The update downloads into the install root, checks the archive's size and SHA-256, runs the unpacked release's launch check, and moves `current` last, so any failure before that leaves the install as it was; see [the updater](../packages/boot/updater/README.md). The launch check runs the new release's own `--self-check` with the running Node, in a private temporary home it removes afterwards, without a TTY, network, or model key, and within 60 seconds: it loads the shipped `tui` and `headless` profiles, the agent presets' plugins, and the terminal's runner modules, as a launch does, so a release missing a package on this platform is refused with `The downloaded Bake <version> did not start; the current install is unchanged:` and the first line of the failure. Releases up to 0.3.6, which have no `--self-check`, are checked by their `--version` instead; a newer release without it is refused.

`bake update --rollback` returns the install to the newest release still installed whose version is older than the current one; right after an update, that is the release it replaced, which an update always keeps. The updater keeps no other history of `current`: a second rollback goes one release further back, while an older one remains, and with none it says there is nothing to roll back to and exits 1. A rollback takes the same lock as an update, runs the same launch check on the release it returns to, and moves `current` the same way, so on any failure `current` stays where it was. It says which versions it moved between, removes nothing, and leaves open sessions on their own release; `bake update` installs the newest release again, reusing its directory when it is still there. Sessions already open keep running their own release; new ones start the new release. A source checkout is refused with the command that updates it.

On Unix, `<install root>/current` is a link that `~/.local/bin/bake` and `~/.local/bin/dsh` follow. On Windows, `bake.cmd` and `dsh.cmd` read the release name from `<install root>\current.txt` on every run, so an update never rewrites the batch file a running `cmd.exe` is reading; an older `bake.cmd` that named one release directly is replaced once the `cmd.exe` running it exits.

The terminal names a newer release in its status line, from an answer cached in `<Bake home>/update-check.json` for an hour, or ten minutes when the check failed, and refreshes that answer in the background for as long as it runs, without delaying the first frame. `bake update` records its own answer there too. The notice never installs anything; once `/update` or `bake update` has installed the release, it asks for a restart instead. `BAKE_NO_UPDATE_CHECK=1` turns the check off, which also keeps the install out of the download service's daily count of active installs. Installs from a release before the updater have no `bake update`; running the installer again brings them onto it.
